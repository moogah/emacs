* Overview

Workspace-relative resolution of Emacs bookmarks.  A bookmark records an
absolute =filename=; when the same file lives in several checkouts of one
repository (a canonical clone plus one git worktree per workspace),
jumping to that bookmark opens whichever checkout happened to be current
when the bookmark was made.  This module stamps portable coordinates onto
new bookmark records and resolves them against the current workspace at
jump time.

** Boundary

This module is a *consumer* of the workspaces package, not part of its
core (=register/boundary/portable-bookmarks-consumer=).  The one-way rule:

- It MAY name =bookmark=, =git=, and workspaces registry internals
  (=workspace--registry=, =workspace--current-name=, =workspace--broken-p=,
  =workspace-restore=, =workspace-anti-save-predicates=).
- Workspaces CORE (=data-model= / =integrations= / =workspaces= / =tabs= /
  =persistence= / =layouts= / =workspaces-mode= / =workspaces-transient=)
  MUST NEVER name a =workspace-bookmark-*= symbol.  The single permitted
  mention in core is the loader PATH STRING "portable-bookmarks.el" in
  =workspaces.org= — a string, not a live symbol.
- One sibling CONSUMER module, =git-worktrees.el=, calls into this one:
  it calls =workspace-bookmark-canonical-checkouts-in-view= and nothing
  else, never =require=s this module, and guards the call with =fboundp=
  at call time.  That function is a cross-module interface with a
  stability promise (see "Cross-module interface: the canonical
  checkouts in view"); every =workspace-bookmark--= symbol stays private.

** No magit, no projectile

Git is reached by subprocess (=process-file=), never through magit.  This
is deliberately the OPPOSITE choice from =git-worktrees.el=, which reaches
worktrees via =magit-list-worktrees= and therefore carries a hard magit
dependency.  Bookmark resolution must not inherit it: bookmarks are a
stock-Emacs facility and this module has to keep working in a session that
has never loaded magit.  The two worktree enumerations are a known,
accepted overlap for this slice
(=register/boundary/portable-bookmarks-consumer= =known_overlap=).

** Droppable

Removing the single =jf/load-module= line in =workspaces.org= removes the
advice and returns behaviour to stock.  Records already stamped keep their
absolute =filename= and keep working — the stamp is additive.  Rollback is
one line.

** Load order

Loaded from the package loader =config/workspaces/workspaces.org=, NOT
from =jf/enabled-modules= in =init.org= (which holds the single entry
=("workspaces/workspaces" …)= for this whole package).  It loads after
=tabs.el= (owner of =workspace--registry= and =workspace--current-name=)
and after =persistence.el= (which defines =workspace-restore=), so the
loader line sits between =workspaces-mode.el= and
=workspaces-transient.el=.

** Scaffold status

Both advice seams are installed.  The STAMP seam is live: a new bookmark
record for a single tracked file or directory inside a repository that
has a remote is stamped with the repository's identity, the location's
repository-relative path, and the stamp-format version.  The JUMP seam is
still deliberately PASS-THROUGH; later tasks (=resolver-outcomes=,
=jump-seam=) fill in its body without moving it.

* Stamped property names

The three properties written into the user's bookmark file.  They are
named here and ONLY here: these symbols end up serialised into
=bookmark-default-file= on the user's disk, so renaming one later would
orphan every existing stamp.  The indirection is cheap insurance against
that.

They are =defconst=, not =defcustom=.  The names are an ON-DISK FORMAT,
not a preference: a user who customised one would silently orphan every
record stamped under the old name, and two machines sharing a bookmark
file with different settings would each read the other's stamps as
unstamped.  Nothing about the format is the user's to choose.

The three are written and read together — a record carries ALL THREE or
NONE (=register/shape/portable-bookmark-coordinates=).  A record carrying
some but not all is malformed and must resolve as =non-portable=, never
to a guess.

The format version exists so that a later change to what the coordinates
MEAN (a different identity normalization, a different relpath convention)
can be told apart from records stamped under this one, instead of being
discovered as a wrong-file open.  A reader that does not recognise the
version treats the record as unstamped.

#+begin_src emacs-lisp
(defconst workspace-bookmark-repo-property 'workspace-bookmark-repo
  "Bookmark-record property holding the repository identity.
The value stored under this property is the normalized remote URL of the
repository the bookmarked location belongs to, for example
\"github.com/moogah/emacs\".

This symbol is serialised into the user's bookmark file.  Changing it
orphans coordinates stamped under the previous name; records so orphaned
degrade to the `non-portable' outcome and behave exactly as stock
bookmarks do.")

(defconst workspace-bookmark-relpath-property 'workspace-bookmark-relpath
  "Bookmark-record property holding the repository-relative path.
The value is the location's path relative to the root of its checkout,
exactly as git spells it: \"lisp/foo.el\" for a file, \"lisp/\" (with a
trailing slash) for a directory, and \"./\" for the repository root
itself.  It can be re-anchored against any checkout of the same
repository with `expand-file-name'.

This symbol is serialised into the user's bookmark file; see
`workspace-bookmark-repo-property' for the consequence of renaming it.")

(defconst workspace-bookmark-format-property 'workspace-bookmark-format
  "Bookmark-record property holding the stamp-format version.
The value is `workspace-bookmark-format-version' at the time the record
was stamped.  This symbol is serialised into the user's bookmark file;
see `workspace-bookmark-repo-property'.")

(defconst workspace-bookmark-format-version 1
  "The stamp-format version this module writes.
Bump it only when the MEANING of the stamped identity or relpath
changes, so records stamped under an older meaning can be recognised
rather than misread.")

* Git subprocess

Every git question this module asks goes through one runner.  Three of
its properties are contractual
(=register/boundary/git-derived-checkout-discovery= =subprocess_contract=):

- =process-file=, never =shell-command-to-string=.  No shell means no
  quoting, which matters concretely here: directory names on this machine
  contain spaces (=~/src/Archived Repos/=).
- =default-directory= is bound to the target directory for every
  invocation, so git answers about the checkout we mean rather than about
  wherever the current buffer happens to live.
- Failure returns nil and NEVER signals.  These helpers run inside
  =bookmark-make-record= and inside a bookmark jump; an error escaping
  into the bookmark machinery would break a core Emacs interaction for a
  peripheral feature.  A non-zero exit, a missing =git= executable, a
  directory that has since been deleted, and empty output all collapse to
  the same nil, and callers map nil to a degraded outcome.

stderr is discarded rather than captured: git writes diagnostics there on
exactly the failures we are deliberately ignoring, and folding them into
stdout would turn a clean nil into a bogus "value".

DIR may name a file rather than a directory — callers hand this helper
bookmark =filename= values.  An EXISTING file is resolved to its
directory.  A DIR that does not exist yields nil; it is NOT resolved to
its parent.  Querying the parent of a missing path answers for whatever
repository encloses that parent, which is a different repository from
the one the caller asked about.  Measured: a checkout named =proj = (with
a trailing space) inside a home that is itself a repository.  A trimmed
=--show-toplevel= spelling =proj= does not exist, and running git in its
parent returned the HOME's identity for a checkout of a different
repository.

*Only =default-directory= decides which repository git answers for.*
Binding it is not enough on its own: git gives =GIT_DIR=,
=GIT_WORK_TREE=, =GIT_COMMON_DIR= and their relatives precedence over the
working directory.  They reach Emacs's =process-environment= when Emacs is
started by git (as =GIT_EDITOR=, or from a hook, which exports =GIT_DIR=),
from a shell that exported them for a bare "dotfiles" repository, or by
=setenv=.  Measured with =GIT_DIR= set: every checkout took the identity of
the repository it named, and =--workspace-checkout= returned a checkout of
a different repository.  The runner therefore unsets every variable git
lists as repository-local (=git rev-parse --local-env-vars=) plus the two
that steer repository discovery (=GIT_CEILING_DIRECTORIES=,
=GIT_DISCOVERY_ACROSS_FILESYSTEM=) and =GIT_NAMESPACE=.  An element
without === in =process-environment= removes that variable from the
subprocess environment, and putting the removals FIRST makes them win over
any duplicate later in the list.

*Output is not trimmed.*  Only the single line terminator git appends is
removed.  Whitespace at either end of a path is part of the path:
=string-trim= turned a checkout named =proj = into =proj=.  Callers that
read several lines split the output themselves.

LOCAL PATHS ONLY.  A remote (TRAMP) DIR is rejected before anything
touches the filesystem, and the whole body sits inside the error barrier.
Three distinct failures are being prevented, in increasing order of harm:

1. =file-directory-p= on a remote name SIGNALS rather than returning nil
   — measured: =/nosuchmethod:host:/tmp= raises =user-error=,
   =/ssh:nonexistent.invalid:/tmp= raises =file-error=.  The caller is
   =bookmark-make-record=, so the contract breach lands in a core Emacs
   interaction.
2. A reachable host is worse than an unreachable one: the probe becomes a
   synchronous network round trip — and =/sudo::= blocks on a password
   prompt — inside bookmark creation.  A hang is not a signal, so the
   =condition-case= would not save us.
3. Worst: =process-file= is TRAMP-aware, so on a reachable host git runs
   ON THAT HOST.  A bookmark for =/ssh:build-box:/srv/emacs/foo.el= would
   be stamped with the identity of the REMOTE checkout, and the resolver
   would later re-point it at a LOCAL worktree — a different machine's
   file, opened silently.  That is exactly
   =register/invariant/no-silent-wrong-file-open=.

A remote file is not portable in this capability's sense anyway: its
identity is the host, not a repo the workspace could hold.  Rejecting it
yields nil, which degrades to the record's stored absolute filename.

#+begin_src emacs-lisp
(defconst workspace-bookmark--git-unset-environment
  '("GIT_DIR" "GIT_WORK_TREE" "GIT_COMMON_DIR" "GIT_INDEX_FILE"
    "GIT_OBJECT_DIRECTORY" "GIT_ALTERNATE_OBJECT_DIRECTORIES"
    "GIT_NAMESPACE" "GIT_CEILING_DIRECTORIES"
    "GIT_DISCOVERY_ACROSS_FILESYSTEM" "GIT_IMPLICIT_WORK_TREE"
    "GIT_PREFIX" "GIT_CONFIG" "GIT_CONFIG_PARAMETERS" "GIT_CONFIG_COUNT"
    "GIT_GRAFT_FILE" "GIT_NO_REPLACE_OBJECTS" "GIT_REPLACE_REF_BASE"
    "GIT_SHALLOW_FILE")
  "Environment variables removed for every git subprocess this module runs.
Each one can make git answer about a repository other than the one
`default-directory' names.")

(defun workspace-bookmark--git (dir &rest args)
  "Run git with ARGS in DIR and return its stdout, or nil.

Only the one line terminator git appends is removed from the output;
other leading and trailing whitespace is kept, because it can be part of
a path.  Returns nil — never signals — when DIR is nil, remote or
missing, when git exits non-zero, or when git produces no output.  If
DIR names an existing file, git is run in the file's directory; a DIR
that does not exist is never resolved to its parent.  stderr is
discarded.  The variables in `workspace-bookmark--git-unset-environment'
are removed from git's environment, so `default-directory' alone decides
which repository git answers for.

DIR must be LOCAL.  A remote (TRAMP) name returns nil without touching
the filesystem: probing one can signal, can block on a password prompt,
and — on a reachable host — would run git remotely and stamp the wrong
machine's identity."
  (condition-case nil
      (let ((path (and (stringp dir)
                       (not (file-remote-p dir))
                       (expand-file-name dir))))
        (when (and path (not (file-remote-p path)))
          (let ((cwd (cond ((file-directory-p path)
                            (file-name-as-directory path))
                           ((file-exists-p path)
                            (file-name-directory (directory-file-name path))))))
            (when (and cwd (file-directory-p cwd))
              (let ((default-directory cwd)
                    (process-environment
                     (append workspace-bookmark--git-unset-environment
                             process-environment)))
                (with-temp-buffer
                  (when (eq 0 (apply #'process-file "git" nil '(t nil) nil args))
                    (let ((out (string-remove-suffix "\n" (buffer-string))))
                      (unless (string-empty-p out) out)))))))))
    (error nil)))
#+end_src

* Same file

Every "are these two paths the same file?" question in this module goes
through one predicate, and it compares FILE IDENTITY: the device and
inode numbers of the two paths' truenames.  Spelling does not matter
(trailing slash, =~=, symlinks, letter case on a case-insensitive disk),
and neither does anything that can change while the file stays the same
file.

=file-equal-p= is NOT used.  In Emacs 30 it truenames and stats each path
and then compares the WHOLE attribute lists with =equal=.  Those lists
include the access, modification and status-change times, so a directory
that is modified, or merely read, between the two stats compares unequal
to itself.  In the ownership test, "not equal" means "not inside this
home", and ownership-first classification then calls a workspace's full
clone =canonical=.  The reviewer measured 4,817 wrong =canonical= answers
in 20,000 =--classify= calls while a shell loop created and removed one
file in the home.  On this APFS volume the first read of a directory after
it changes also updates its access time, so any concurrent reader
(Spotlight, a sync client, git in another process) is enough.

Nil when either path is not a local string or does not exist.  Remote
names are rejected before any filesystem call, as everywhere else in this
module.

#+begin_src emacs-lisp
(defun workspace-bookmark--same-file-p (a b)
  "Return non-nil when A and B name the same existing local file.

Compares the device and inode numbers of the two paths' truenames, so
spelling, symlinks and timestamps do not matter.  `file-equal-p' is
deliberately not used: it compares whole attribute lists, timestamps
included, and so reports a directory modified between its two stats as
unequal to itself.  Nil when either is not a string, is remote, or does
not exist.  Never signals."
  (and (stringp a) (stringp b)
       (not (file-remote-p a))
       (not (file-remote-p b))
       (condition-case nil
           (let ((attrs-a (file-attributes (file-truename (expand-file-name a))))
                 (attrs-b (file-attributes (file-truename (expand-file-name b)))))
             (and attrs-a attrs-b
                  (file-attribute-inode-number attrs-a)
                  (file-attribute-device-number attrs-a)
                  (equal (file-attribute-inode-number attrs-a)
                         (file-attribute-inode-number attrs-b))
                  (equal (file-attribute-device-number attrs-a)
                         (file-attribute-device-number attrs-b))))
         (error nil))))
#+end_src

** Which repository this is

=origin= is preferred.  When there is no =origin= and there is EXACTLY
ONE remote, that one is used, so a checkout whose only remote is named
=upstream= still has an identity instead of silently degrading to "no
remote".  A repository with no remote at all returns nil, and that is the
whole answer: NO REMOTE MEANS NO IDENTITY.  A path-based fallback would be
meaningless on another machine, which is the one thing this capability
exists to survive.  On this machine 9 of 51 repositories under =~/src=
have no remote, so the nil branch is a normal case, not an edge case.

Two corrections to the obvious implementation, both of which produce a
CONFIDENTLY WRONG identity rather than a missing one:

=git remote get-url=, NOT =git config --get remote.origin.url=.  The
config value is raw; =get-url= is the effective URL.  Measured on a
throwaway repo: with =url."git@github.com:".insteadOf "gh:"=, the config
read returns =gh:moogah/emacs.git=, which normalizes to the fabricated
host =gh/moogah/emacs= — an identity that exists only in one machine's
gitconfig, and therefore precisely the cross-machine breakage this
capability exists to prevent.  =get-url= returns the expanded
=git@github.com:moogah/emacs.git=.  The same command also reads the LAST
value of a multi-valued =remote.origin.url= while git fetches the FIRST.
(The common =https= ↔ =ssh= =insteadOf= rewrite is harmless here, because
both spellings normalize equal; it is the shorthand aliases that break.)

SOLE remote, not FIRST remote.  =git remote= lists alphabetically, so
"first" makes the identity depend on remote NAMES: adding a remote called
=backup= to a repo whose only remote was =upstream= would silently re-key
every bookmark already stamped from it — the stamps are persisted, so they
are orphaned, not recomputed.  Ambiguity must degrade to nil, not to a
guess.

#+begin_src emacs-lisp
(defun workspace-bookmark--remote-url (dir)
  "Return the effective remote URL of the repository containing DIR, or nil.

`origin' is preferred.  When the repository has no `origin' but has
exactly ONE remote, that remote is used.  Returns nil when the repository
has no remote, when it has several and none is `origin', or when DIR is
in no repository.

Uses `git remote get-url', which expands `url.*.insteadOf' rewrites and
yields the URL git actually uses.  `git config --get remote.origin.url'
would return the raw, machine-local spelling."
  (or (workspace-bookmark--git dir "remote" "get-url" "origin")
      (let ((remotes (split-string
                      (or (workspace-bookmark--git dir "remote") "")
                      "\n" t "[ \t\r]+")))
        (when (= 1 (length remotes))
          (workspace-bookmark--git dir "remote" "get-url" (car remotes))))))
#+end_src

** Normalizing a remote URL to an identity

The single canonical translation between git's several spellings of one
remote and the single string persisted in
=register/shape/portable-bookmark-coordinates=.  Inlining it at a second
site is exactly the boundary-translation drift the register tier exists to
catch, so every producer goes through this function.

These must all normalize to =github.com/moogah/emacs=:

: git@github.com:moogah/emacs.git
: https://github.com/moogah/emacs
: ssh://git@github.com/moogah/emacs.git

*** The colon is two different things

git's remote syntax has two forms, and the colon means something different
in each:

- With an explicit scheme (=ssh://=, =https://=, =git://=) the URL is
  =scheme://[userinfo@]host[:PORT]/path= — a colon after the host
  introduces a PORT.
- Without a scheme, git reads the scp-like form =[userinfo@]host:path= —
  the colon is the path separator and there is NO port.  In
  =git@example.com:2222/team/repo.git= the =2222= is a directory name.

The scheme therefore selects the branch EXCLUSIVELY: a URL that has a
scheme but does not parse as one is nil, never retried as scp-like
syntax.  Falling through would read =https://github.com= as scp-like,
taking =https= for the host and =github.com= for the path — a WRONG
identity rather than an absent one, which is the difference between a
bookmark that degrades and a bookmark that resolves somewhere else.

So the disambiguation has to happen BEFORE the scheme is stripped: a rule
set that strips =scheme://= first and only then "converts the SSH
=host:path= colon to =/=" cannot tell the two apart any more, and turns
=ssh://git@example.com:2222/team/repo.git= into
=example.com/2222/team/repo= — which does not match the HTTPS spelling of
the same repository, defeating the whole point of normalizing.  A port is
transport, not identity, so with a scheme present the port is DROPPED.

*** Userinfo is stripped, and that is a privacy property too

=https://TOKEN@github.com/moogah/emacs.git= is a real shape for a
credential-embedded remote.  Since the identity is written into the user's
bookmark file on disk, keeping userinfo would persist a secret into a file
this capability had no business writing secrets into.  Everything before
the =@= goes, password form included.

*** Host is downcased, path is not

Hosts are case-insensitive, so downcasing the host is free.  Paths are NOT
downcased even though the major forges treat them case-insensitively,
because the two failure modes are not symmetric: keeping path case can at
worst make two spellings of ONE repository look like two (which degrades
to an unstamped or non-portable bookmark — safe), while downcasing can
make two DIFFERENT repositories on a case-sensitive host collide, which
would open the wrong file (=register/invariant/no-silent-wrong-file-open=).

*** No host, no identity

Anything that does not yield an explicit =host/path= returns nil.  This is
load-bearing, not merely tidy: a local remote (=/srv/git/repo.git=,
=file:///srv/git/repo.git=, =../sibling=) names a location on THIS
machine, so it is no more portable than the absolute filename the bookmark
already carries.  The two regexps below reject those by construction — a
local absolute path cannot start a host, and a relative path has no colon
before its first slash.

#+begin_src emacs-lisp
(defconst workspace-bookmark--scheme-prefix-re
  "\\`[a-zA-Z][a-zA-Z0-9+.-]*://"
  "Match the leading SCHEME:// of a remote URL.
Which branch of `workspace-bookmark--normalize-identity' applies is
decided by this alone.  A URL that has a scheme but does not parse is
nil, never retried as scp-like syntax: \"https://github.com\" read as
scp-like would yield the host \"https\".")

(defconst workspace-bookmark--scheme-url-re
  "\\`[a-zA-Z][a-zA-Z0-9+.-]*://\\(?:[^/@]*@\\)?\\([^/:]*\\)\\(?::[0-9]*\\)?/+\\(.*\\)\\'"
  "Match a remote URL carrying an explicit scheme.
Group 1 is the host, group 2 the path.  Any userinfo and any :PORT are
matched and discarded.  A `file://' URL has an empty host and is
therefore rejected downstream.")

(defconst workspace-bookmark--scp-url-re
  "\\`\\(?:[^/@]*@\\)?\\([^/:]+\\):\\(.*\\)\\'"
  "Match git's scp-like remote syntax, [USERINFO@]HOST:PATH.
Group 1 is the host, group 2 the path.  There is no port in this form:
git reads everything after the colon as the path.")
#+end_src

#+begin_src emacs-lisp
(defun workspace-bookmark--normalize-identity (url)
  "Return the normalized repository identity of URL, or nil.

The identity is HOST/PATH, with the scheme, any userinfo, any port, a
trailing \".git\" (in any case) and any trailing slash removed, runs of
slashes collapsed, and the host — but not the path — downcased.  The SSH, HTTPS and ssh:// spellings of one
repository therefore compare `equal'.

Returns nil for anything that does not name a host: local paths,
`file://' URLs, and malformed input."
  (when (stringp url)
    (let ((url (string-trim url))
          host path)
      (cond
       ((string-match-p workspace-bookmark--scheme-prefix-re url)
        (when (string-match workspace-bookmark--scheme-url-re url)
          (setq host (match-string 1 url)
                path (match-string 2 url))))
       ((string-match workspace-bookmark--scp-url-re url)
        (setq host (match-string 1 url)
              path (match-string 2 url))))
      (when (and host path)
        (setq host (downcase host))
        (setq path (replace-regexp-in-string "/+" "/" path))
        (setq path (replace-regexp-in-string "\\`/+" "" path))
        (setq path (replace-regexp-in-string "/+\\'" "" path))
        (when (string-suffix-p ".git" path t)
          (setq path (substring path 0 -4)))
        (setq path (replace-regexp-in-string "/+\\'" "" path))
        (unless (or (string-empty-p host) (string-empty-p path))
          (concat host "/" path))))))
#+end_src

** The composed question

=workspace-bookmark--identity= is the one entry point callers use.  The
remote is looked up at the REPOSITORY ROOT rather than at DIR: the root is
already known by then, it is guaranteed to exist and to be a directory,
and it keeps the "which repository" question anchored to the checkout
=--show-toplevel= actually resolved.  For a linked worktree this still
works, because =remote.origin.url= lives in the shared config the worktree
reads through.

The second half of that question — "given a root, what is its identity?"
— is its own function, because the stamp path already knows the root
(it gets it from the same =rev-parse= that places the location) and asks
through the memo below rather than through =--identity=.

#+begin_src emacs-lisp
(defun workspace-bookmark--root-identity (root)
  "Return the normalized identity of the checkout whose root is ROOT, or nil.
ROOT must already be a checkout root; see `workspace-bookmark--identity'
for the version that finds it."
  (workspace-bookmark--normalize-identity
   (workspace-bookmark--remote-url root)))

(defun workspace-bookmark--identity (dir)
  "Return the normalized identity of the repository containing DIR, or nil.

Returns nil — never signals — when DIR is in no git repository, when that
repository has no remote, or when the remote URL names no host."
  (let ((root (workspace-bookmark--repo-root dir)))
    (and root (workspace-bookmark--root-identity root))))
#+end_src

** Memoised per repository root

Stamping runs inside =bookmark-make-record=, and workspaces' own layout
save calls =bookmark-make-record= for EVERY live buffer on EVERY save —
including the idle-tick autosave.  Unmemoised, each of those records
would pay one to three extra =git remote= subprocesses to rediscover an
answer that almost never changes.  So identity is computed at most once
per repository root, and only the per-location questions (where is this
path, is it tracked) are asked each time.

Two decisions about what the memo holds:

- *A nil answer is memoised too.*  "No remote" is the normal case for 9
  of 51 repositories here, and it is exactly the case that would
  otherwise re-query on every save, forever.
- *It is validated, not trusted.*  Each entry carries the modification
  time of the repository's shared =config= file, which is where =git
  remote add=, =git remote set-url= and =git remote remove= write.  The
  stamp path already learns that file's location from the =rev-parse= it
  runs anyway (=--git-common-dir=), so checking it costs one =stat= and no
  subprocess.  Without this, re-pointing =origin= mid-session would keep
  stamping the OLD identity into new, persisted records.  What it does
  NOT see: anything outside the repository's own =config= that
  =git remote get-url= honours — =url.*.insteadOf= rewrites in the global
  (=~/.gitconfig=, =~/.config/git/config=) or system gitconfig, an
  =include.path= / =includeIf= target, or =config.worktree=.  That blind
  spot is accepted and documented:
  =M-x workspace-bookmark-clear-identity-cache= covers it.  (Filesystems
  with coarse mtimes can also hide two config writes within one tick;
  the same command covers that.)
- *No stamp, no reuse.*  When the config file's modification time
  cannot be read, the stamp is nil.  An entry with a nil stamp would
  match every later nil stamp and never be revalidated, so a nil stamp
  never counts as a hit: identity is recomputed.  This is the failure
  that let a wrongly-resolved common dir freeze a stale identity (see
  "Where a location sits in its checkout").
- *It does not survive a reload.*  The memo holds the OUTPUT of
  =workspace-bookmark--normalize-identity=.  A =defvar= keeps its value
  when the file is loaded again, so after an edit to the normalizer
  followed by =jf/reload-module=, the session would go on persisting
  identities the OLD normalizer produced until each repository's config
  happened to change.  The memo is therefore emptied every time this file
  is loaded (the top-level form after the definitions below).

The key is the checkout ROOT, not the shared git directory, so each
linked worktree has its own entry.  That costs one lookup per worktree
per session and keeps the key identical to what =--show-toplevel=
reports.

#+begin_src emacs-lisp
(defvar workspace-bookmark--identity-memo (make-hash-table :test #'equal)
  "Memoised repository identities, keyed by checkout root.
Each value is (STAMP . IDENTITY), where STAMP is the value
`workspace-bookmark--config-stamp' returned when IDENTITY was computed
and IDENTITY may be nil.")

(defun workspace-bookmark-clear-identity-cache ()
  "Forget every memoised repository identity.

Each memoised identity is revalidated against the modification time of
its repository's own git config, so `git remote add', `set-url' and
`remove' are picked up without this command.  It is needed only after a
change the memo cannot see: a `url.*.insteadOf' rule (or anything else
`git remote get-url' honours) added to the global, XDG or system
gitconfig, to an included config file, or to `config.worktree'.  Loading
this module clears the memo too."
  (interactive)
  (clrhash workspace-bookmark--identity-memo))

(defun workspace-bookmark--config-stamp (git-common-dir)
  "Return the modification time of GIT-COMMON-DIR's config file, or nil."
  (and git-common-dir
       (file-attribute-modification-time
        (file-attributes (expand-file-name "config" git-common-dir)))))

(defun workspace-bookmark--memoised-identity (root git-common-dir)
  "Return the identity of the checkout at ROOT, memoised per ROOT.
GIT-COMMON-DIR is the repository's shared git directory; the memoised
value is reused only while its config file is unchanged, and never when
that file's modification time cannot be read.  A nil identity is
memoised like any other."
  (let ((stamp (workspace-bookmark--config-stamp git-common-dir))
        (hit (gethash root workspace-bookmark--identity-memo)))
    (if (and hit stamp (equal (car hit) stamp))
        (cdr hit)
      (let ((identity (workspace-bookmark--root-identity root)))
        (puthash root (cons stamp identity) workspace-bookmark--identity-memo)
        identity))))
#+end_src

#+end_src

* Seam 1 — stamp on ~bookmark-make-record~

=:filter-return= advice on =bookmark-make-record=.  It receives the record
Emacs just built and returns it either stamped or byte-identical.  It must
never prompt, message, or alter the bookmark name the user chose, and a
failure to stamp must never prevent a bookmark from being created — hence
the =condition-case= returning the ORIGINAL record
(=register/boundary/bookmark-advice-seams= seam 1).

Every record =bookmark-make-record= builds passes through here — a
user's =C-x r m=, and also workspaces' own layout save, which calls it
for every live buffer.  Layout records are stamped exactly like a user's
bookmarks, deliberately: the caller is not detected or excluded.

** Which records are Tier 1

The gate.  It answers "is this value even a path?" before anything
treats it as one, and it answers WITHOUT running git, so a record it
rejects costs no subprocess at all.

- The =filename= must be a string and ABSOLUTE.  A relative value is not
  a location this record can be said to have: the real bookmark file
  here has four =tab-bookmark= records whose =filename= is the label
  ="3 buffers"=, and =expand-file-name= would happily turn that into a
  path under whatever =default-directory= happens to be.
- It must be LOCAL.  A TRAMP name is rejected before any filesystem
  call, for the reasons given under the git runner (a probe can signal,
  hang on a password prompt, or run git on the remote host).
- It must name something that EXISTS.
- A =buffer= or =window= property holding anything but a string marks
  a nested sub-record or a window tree — Tier 2 territory, where
  rewriting naively would corrupt shared or circular structure.

=filename= is often abbreviated (=bookmark-buffer-file-name= writes
=~/…=), so the returned location is expanded.

#+begin_src emacs-lisp
(defun workspace-bookmark--record-location (record)
  "Return the single local file or directory RECORD refers to, or nil.

RECORD is a bookmark record (NAME . ALIST).  Returns the expanded
`filename' only when it is an absolute, local (non-TRAMP) path naming an
existing file or directory, and RECORD carries no nested sub-record or
window tree (a `buffer' or `window' property whose value is not a
string).  Runs no subprocess."
  (let ((filename (bookmark-prop-get record 'filename)))
    (and (stringp filename)
         (file-name-absolute-p filename)
         (not (file-remote-p filename))
         (not (seq-some (lambda (prop)
                          (let ((value (bookmark-prop-get record prop)))
                            (and value (not (stringp value)))))
                        '(buffer window)))
         (let ((location (expand-file-name filename)))
           (and (not (file-remote-p location))
                (file-exists-p location)
                location)))))
#+end_src

** Where a location sits in its checkout

One =rev-parse= answers three questions at once: the checkout root
(=--show-toplevel=), the shared git directory whose =config= validates the
identity memo (=--git-common-dir=), and the path from the root to the
directory git ran in (=--show-prefix=).  git prints one per line, in
argument order.

Two spellings need care:

- At the repository root the prefix is the EMPTY string: git prints an
  empty line.  The runner removes only git's final line terminator, so
  that empty line is still there and three lines come back, the last
  one empty.
- =--git-common-dir= is asked with =--path-format=absolute=.  Without
  it git answers RELATIVE to the directory it ran in (=../../.git=),
  and it runs in the RESOLVED directory, not in the spelling the caller
  passed.  Through a symlink to a repository SUBDIRECTORY
  (=L/linksub -> R/sub=), expanding =../../.git= against the caller's
  =L/linksub/deep/= named =L/.git= instead of =R/.git=.  The memo then
  validated against a config file that does not exist, got a nil stamp
  and matched it forever, so a =git remote set-url= was never noticed
  and the OLD identity kept being stamped (measured).  The flag needs
  git 2.31; an older git exits non-zero and the position is nil.

Anything other than three lines (a checkout path containing a newline,
say) is refused rather than parsed.

For a DIRECTORY location the same call also asks a fourth question:
=HEAD:./=, the object id of DIR's own tree in HEAD.  That is the bounded
"does git know this directory?" check (see "The repository-relative path"
below): git resolves one tree entry per path component and prints one
line, however large the subtree.  If DIR is not in HEAD — or there is no
HEAD — =rev-parse= exits non-zero and the whole position is nil.  With
the fourth argument exactly FOUR lines come back.

#+begin_src emacs-lisp
(defun workspace-bookmark--checkout-position (dir &optional committed)
  "Return (ROOT GIT-COMMON-DIR PREFIX [TREE]) for directory DIR, or nil.

ROOT is the checkout root as a directory name, GIT-COMMON-DIR the
absolute shared git directory, and PREFIX DIR's path relative to ROOT as
git spells it (\"sub/dir/\", or \"\" at the root).  One git subprocess.
Nil when DIR is in no work tree.

With COMMITTED non-nil, also return TREE, the object id of DIR's tree in
HEAD, and return nil when DIR is not in HEAD or there is no HEAD.  The
cost is bounded by DIR's depth, not by the size of its subtree."
  (let* ((out (apply #'workspace-bookmark--git
                     dir "rev-parse"
                     "--path-format=absolute" "--show-toplevel" "--git-common-dir"
                     "--show-prefix"
                     (and committed '("HEAD:./"))))
         (lines (and out (split-string out "\n"))))
    (when (and (= (length lines) (if committed 4 3))
               (file-name-absolute-p (nth 0 lines))
               (file-name-absolute-p (nth 1 lines)))
      (append (list (file-name-as-directory (nth 0 lines))
                    (nth 1 lines)
                    (nth 2 lines))
              (and committed (list (nth 3 lines)))))))
#+end_src

** The repository-relative path

The relpath comes from GIT, never from string arithmetic on two paths.
Asking git settles, in one move, the questions arithmetic gets wrong:
symlinked temp directories (=/var= vs =/private/var=), case-insensitive
filesystems, and whether the location is in this repository at all.

*UNTRACKED MEANS UNSTAMPED.*  A location git does not report is returned
as nil and the record is left exactly as stock Emacs made it — no
fallback path computation.

*Files.*  =git ls-files --full-name= on the file's BASENAME, run in its
directory.  Three flags are load-bearing:

- =-z=: without it git C-quotes any path with non-ASCII, ="= or =\=
  (=café.txt= comes back as ="caf\303\251.txt"=, quotes included).
  =-z= prints raw bytes, NUL-terminated.
- =--literal-pathspecs=: pathspecs are GLOBS by default.  Measured: in a
  repository tracking both =glob[1].txt= and =glob1.txt=, asking about
  =glob[1].txt= returns BOTH.  Literal pathspecs return exactly one.
- =--=: a file named =-v= is a path, not an option.

During a merge conflict the index holds the path once per STAGE (base,
ours, theirs), and =ls-files= prints it once for each.  The reported names
are deduplicated before the "exactly one path" rule is applied, so a file
bookmarked mid-merge, which is when people bookmark, is still stamped.

The basename rather than the absolute name, because it is the question
git is built for: the runner has already put =default-directory= in the
file's directory.  (Measured: an absolute name through the =/tmp= →
=/private/tmp= symlink also works with git 2.49, but the basename leaves
nothing to depend on.)

*Directories.*  =ls-files= is the WRONG question for a directory — it
lists every tracked file beneath it, not the directory's own path.  The
git-native answer is =--show-prefix= from inside it, which
=--checkout-position= already has.

"Tracked", for a directory, means git knows it: it is a tree in HEAD.
That is asked in the SAME =rev-parse= (=HEAD:./=), so a directory record
costs ONE subprocess and its cost does not depend on how many files it
holds.  An earlier revision asked =ls-files -- .= for "at least one
tracked file under it", which prints the entire subtree just to test it
for emptiness — measured by the architect at 39 ms and 2.6 MB of output
for the root of a 50,000-file repository, and the root is the common
case (a Dired or =magit-status= buffer on a checkout root).  =ls-files=
has no way to stop at the first match, so the check moved to HEAD.

- *The root* is a tree in HEAD whenever there is a HEAD, so it is
  tracked by definition and pays nothing extra.  An unborn repository
  (no commit yet) has no HEAD, and its root is unstamped.
- *The cost of asking HEAD rather than the index*: a NEW directory whose
  files are staged but never committed is unstamped until its first
  commit.  That degrades (the record keeps its absolute =filename=); it
  never stamps a wrong path.  Files inside it are still stamped, because
  files are asked of the index.
- An empty or wholly untracked directory is not in HEAD, so it is
  unstamped, exactly as before.

*The repository root* has an empty prefix.  It is stored as =./=, not as
=""=:

- all three properties must be present AND meaningful, and an empty
  string is the value every emptiness check (=string-empty-p=,
  =seq-empty-p=, a sloppy =(and relpath …)= in another language) reads
  as "missing";
- every directory relpath then ends in =/=, so file and directory
  relpaths stay distinguishable by spelling alone;
- it re-anchors with the same call as every other relpath:
  =(expand-file-name "./" root)= is =root= itself, with its slash.

*Verification.*  The relpath git reports is accepted only if, anchored
back on the root, it names the SAME file as the location
(=workspace-bookmark--same-file-p= compares the files, not the strings).
This turns any git answer we misparsed into "unstamped" instead of into a
persisted wrong path.

Output is decoded as UTF-8 regardless of locale: a GUI Emacs can start
with a non-UTF-8 =default-process-coding-system=, and the raw =-z= bytes
would then decode into a relpath naming nothing.

#+begin_src emacs-lisp
(defconst workspace-bookmark--root-relpath "./"
  "The relpath stamped for the repository root itself.
git spells the root's prefix as the empty string; see
`workspace-bookmark-relpath-property' for why it is stored as \"./\".")

(defun workspace-bookmark--relpath (location position)
  "Return LOCATION's repository-relative path, or nil when git does not track it.

POSITION is (ROOT GIT-COMMON-DIR PREFIX) from
`workspace-bookmark--checkout-position' for the directory holding
LOCATION (LOCATION itself, when it is a directory).  A file's relpath is
what `git ls-files --full-name' reports for it.  A directory's is its
PREFIX (`workspace-bookmark--root-relpath' at the root), and only when
POSITION carries the directory's HEAD tree (see
`workspace-bookmark--checkout-position').  Merge-conflict stages are
collapsed, so a conflicted file still has one relpath.  The result must
re-anchor on ROOT to the same file as LOCATION, or nil is returned."
  (let* ((root (nth 0 position))
         (relpath
          (if (file-directory-p location)
              (and (nth 3 position)
                   (let ((prefix (nth 2 position)))
                     (if (string-empty-p prefix)
                         workspace-bookmark--root-relpath
                       prefix)))
            (let ((reported (split-string
                             (or (workspace-bookmark--git
                                  location "--literal-pathspecs" "ls-files"
                                  "-z" "--full-name" "--"
                                  (file-name-nondirectory location))
                                 "")
                             "\0" t)))
              (setq reported (delete-dups reported))
              (and (= 1 (length reported)) (car reported))))))
    (and relpath
         (workspace-bookmark--same-file-p (expand-file-name relpath root) location)
         relpath)))
#+end_src

** Coordinates

The sole producer of the identity/relpath pair
(=register/shape/portable-bookmark-coordinates=).  The order of the
questions is chosen for the hot path: place the location (one
subprocess), then ask whether git tracks it (one more for a file; for a
directory the placing call has already answered), and only then ask for
identity — which, through the memo, is usually free.  A file outside any
repository costs one subprocess; an untracked file costs two and never
reaches the remote lookup; a directory, at any depth and of any size,
costs one.

#+begin_src emacs-lisp
(defun workspace-bookmark--coordinates (location)
  "Return (IDENTITY . RELPATH) for the local file or directory LOCATION, or nil.

Nil when LOCATION is in no git work tree, when git does not track it,
or when its repository has no usable remote.  LOCATION must already
have passed `workspace-bookmark--record-location'."
  (let* ((coding-system-for-read 'utf-8-unix)
         (coding-system-for-write 'utf-8-unix)
         (directory-p (file-directory-p location))
         (dir (if directory-p
                  (file-name-as-directory location)
                (file-name-directory location)))
         (position (workspace-bookmark--checkout-position dir directory-p))
         (relpath (and position (workspace-bookmark--relpath location position)))
         (identity (and relpath
                        (workspace-bookmark--memoised-identity
                         (nth 0 position) (nth 1 position)))))
    (and identity (cons identity relpath))))
#+end_src

** Stamping

The stamped record is built FRESH rather than by =bookmark-prop-set= on
the record Emacs handed us.  That is what makes "all three or none" hold
by construction: every fallible step (the gate, git, the memo) finishes
before anything is built, and building is a single =cons= onto a copied
list, so there is no state in which one property has been written and
the next has not.  It also means the record we return on the error path
really is the ORIGINAL, unmutated — and a handler that returned a shared
or literal record is never written through.

Every original property is kept, in order, with =filename= untouched: it
is the absolute fallback every degraded outcome relies on and the reason
a stock Emacs can still read the file.  Any stale copies of the three
stamped properties are dropped before the fresh ones are appended, so a
record can never carry two of one.

#+begin_src emacs-lisp
(defun workspace-bookmark--with-coordinates (record coordinates)
  "Return a new record: RECORD's name and properties plus COORDINATES.

COORDINATES is (IDENTITY . RELPATH).  The three stamped properties are
appended together after RECORD's own properties, replacing any earlier
copies of them.  RECORD itself is not modified."
  (let ((stamped (list (cons workspace-bookmark-repo-property (car coordinates))
                       (cons workspace-bookmark-relpath-property (cdr coordinates))
                       (cons workspace-bookmark-format-property
                             workspace-bookmark-format-version))))
    (cons (car record)
          (append (seq-remove (lambda (prop)
                                (and (consp prop) (assq (car prop) stamped)))
                              (bookmark-get-bookmark-record record))
                  stamped))))
#+end_src

#+begin_src emacs-lisp
(defun workspace-bookmark--stamp-record (record)
  "Return RECORD with portable coordinates added, or RECORD unchanged.

Intended as `:filter-return' advice on `bookmark-make-record'.  A record
for a single tracked file or directory inside a repository with a remote
comes back as a NEW record carrying all three stamped properties
\(`workspace-bookmark-repo-property', `workspace-bookmark-relpath-property',
`workspace-bookmark-format-property'); any other record comes back
unchanged and `eq' to RECORD.

Never prompts, never messages, never touches the bookmark name.  Any
internal error is swallowed and the original RECORD returned: failing to
stamp must not prevent a bookmark from being created."
  (condition-case nil
      (let* ((location (workspace-bookmark--record-location record))
             (coordinates (and location
                               (workspace-bookmark--coordinates location))))
        (if coordinates
            (workspace-bookmark--with-coordinates record coordinates)
          record))
    (error record)))
#+end_src

* Checkout discovery

Where else is this repository checked out, and which of those checkouts —
if any — may be offered as THE canonical one?  These are pure queries: no
buffer is opened, nothing prompts, nothing is cached.  Every git question
goes through =workspace-bookmark--git=, every identity through
=workspace-bookmark--identity=, and every function here returns nil (or,
for the classifier, =other=) rather than signalling
(=register/boundary/git-derived-checkout-discovery=).

The vocabulary is closed: each checkout is =canonical=,
=workspace-owned= or =other= (=register/vocabulary/checkout-classification=).
Its whole reason to exist is one NEGATIVE rule: a workspace-owned checkout
is never canonical, and neither is a linked worktree that no workspace
owns.  Offering either as "the canonical checkout" would reintroduce the
defect this capability removes — one workspace's files opened while the
user is in another, or a stale branch shown as if it were the repository.

** What counts as a checkout

A directory is a usable checkout when it is LOCAL, exists, and contains a
=.git= entry.  The =.git= entry may be a directory (a main worktree) or a
file (a linked worktree, a submodule, a =--separate-git-dir= checkout);
either way git will treat the directory as a checkout root.

The existence test is load-bearing, not tidy.  =git worktree list= reports
worktrees whose directory is gone (=prunable=), a bare repository as its
first entry, and — for a submodule or a =--separate-git-dir= repository —
the GIT DIRECTORY in place of the main worktree (measured, git 2.49).  All
of those are real directories or recorded paths that are not checkouts,
and a consumer handed one would open files that are not there.

#+begin_src emacs-lisp
(defun workspace-bookmark--checkout-dir-p (dir)
  "Return non-nil when DIR is an existing local checkout root.
That is: DIR is a local directory containing a `.git' file or directory.
Never signals; a remote DIR is rejected without touching the network."
  (and (stringp dir)
       (not (file-remote-p dir))
       (condition-case nil
           (let ((dir (expand-file-name dir)))
             (and (file-directory-p dir)
                  (file-exists-p (expand-file-name ".git" dir))))
         (error nil))))
#+end_src

** Reading =git worktree list --porcelain=

The porcelain form, not the human-readable one: the latter is
column-aligned and lossy.  Porcelain is one attribute per line; each entry
starts with =worktree <path>= and git lists the MAIN worktree first.  The
flag lines that matter here are =bare=, =detached=, =locked [reason]= and
=prunable [reason]=; =HEAD= and =branch= are ignored.

=-z= is deliberately NOT used.  It is the only fully faithful form (a
worktree path containing a newline splits across two lines without it),
but it needs git 2.36, and on an older git the call exits non-zero, which
this module maps to "no checkouts" — a silent loss of the whole feature
on, for example, Ubuntu 22.04's git 2.34, traded for a path spelling
nobody uses.  Without =-z= such a path is read truncated at the newline;
the truncated path does not name a checkout, so the existence test in
=workspace-bookmark--checkout-dir-p= drops it: the entry goes missing, it
is never replaced by a different directory.

#+begin_src emacs-lisp
(defun workspace-bookmark--parse-worktree-porcelain (text)
  "Parse TEXT, output of `git worktree list --porcelain', into entries.

Returns a list of plists in git's order, the main worktree first:

  (:path PATH :bare BOOL :detached BOOL :locked BOOL :prunable BOOL)

Lines before the first `worktree' line, and attribute lines this parser
does not know, are ignored.  TEXT nil yields nil."
  (let (entries current)
    (dolist (line (split-string (or text "") "\n"))
      (cond
       ((string-match "\\`worktree \\(.+\\)\\'" line)
        (when current (push current entries))
        (setq current (list :path (match-string 1 line)
                            :bare nil :detached nil
                            :locked nil :prunable nil)))
       ((null current))
       ((string-match-p "\\`bare\\'" line)
        (setq current (plist-put current :bare t)))
       ((string-match-p "\\`detached\\'" line)
        (setq current (plist-put current :detached t)))
       ((string-match-p "\\`locked\\(?: \\|\\'\\)" line)
        (setq current (plist-put current :locked t)))
       ((string-match-p "\\`prunable\\(?: \\|\\'\\)" line)
        (setq current (plist-put current :prunable t)))))
    (when current (push current entries))
    (nreverse entries)))

** The canonical checkout

The repository's MAIN worktree, established by two independent signals
that must agree, and then confirmed against the candidate itself:

1. =git rev-parse --path-format=absolute --git-common-dir= — the shared
   git directory.  When it is a directory literally named =.git=, its
   parent is the main worktree.
2. The FIRST entry of =git worktree list --porcelain=, which git documents
   as the main worktree.  It must not be =bare=.
3. =git rev-parse --show-toplevel=, run IN the candidate, must name the
   candidate.  This catches the one layout where 1 and 2 agree and are
   both wrong (see the =core.worktree= row below).  It costs one more
   subprocess, paid only once 1 and 2 have agreed.
4. The candidate must HOLD the work tree: at least one path =git
   ls-files= lists there exists under it.  This catches the layouts
   where all three checks above agree on a directory that holds nothing
   but the git directory (the two =.git=-named rows below).  One more
   subprocess, paid only once 1–3 have passed.

=--path-format=absolute= is required, not cosmetic.  Asked in the main
worktree, plain =--git-common-dir= answers =.git=, and from a
subdirectory =../.git= — relative to wherever git happened to run.  The
runner resolves a file argument to its directory before running git, so
re-expanding that answer against the caller's DIR would be wrong whenever
DIR names a file.  The flag needs git 2.31; an older git exits non-zero
and the answer is nil.

The signals disagree in exactly the cases where the naive answer is a
GUESS, and every one of them resolves to nil (measured, git 2.49):

| layout                                  | common dir        | first entry         | parent-of-common would give  |
|-----------------------------------------+-------------------+---------------------+------------------------------|
| ordinary clone                          | =R/.git=          | =R=                 | =R= (correct — agree)        |
| bare =R.git= + linked worktrees         | =R.git=           | =R.git=, =bare=     | the directory ABOVE =R.git=  |
| bare repo stored as =D/.git= + worktrees | =D/.git=          | =D/.git=, =bare=    | =D=, which has no work tree  |
| =git init --separate-git-dir G W=       | =G=               | =G= (not =W=!)      | the parent of =G=            |
| submodule =S/m=                         | =S/.git/modules/m= | =S/.git/modules/m=  | =S/.git/modules=             |
| =D/.git= with =core.worktree = T=       | =D/.git=          | =D=                 | =D= — but the work tree is =T= |
| =git init --separate-git-dir P/.git W=  | =P/.git=          | =P=                 | =P= — a husk holding only =.git= |
| =W/.git= a symlink to =P/.git=          | =P/.git=          | =P=                 | =P= — a husk holding only =.git= |

The =--separate-git-dir= row holds only when the git directory is NOT
named =.git=.  When it is — =git init --separate-git-dir=<elsewhere>/.git=,
or a main worktree whose =.git= is a symlink to a directory kept on
another disk or outside a sync folder — the last two rows apply, and
every signal agrees on the wrong directory.  Git's absolute common dir is
the RESOLVED git directory =P/.git=; its main-worktree slot is that path
minus =/.git=; and git run IN =P= finds =P/.git= and treats =P= as a
work tree, so =--show-toplevel= names =P= and =P='s own git dir IS the
common dir.  Nothing git says distinguishes =P= from a real main
worktree.  Only the disk does: =P= holds none of the files git's index
lists (measured, git 2.49).  Hence check 4.

Check 4 asks for a TRACKED path, not merely "something besides =.git=":
a husk that Finder, Spotlight or a sync client has visited holds a
=.DS_Store= or similar, and would pass the weaker test.  The price is
that a main worktree tracking no files, or one whose every tracked file
has been deleted, has no canonical checkout — which costs nothing, since
an untracked location is never stamped.

A tracked path is not enough on its own either.  Repositories edited on
a Mac often COMMIT a =.DS_Store=, and Windows and sync clients leave
=Thumbs.db=, =desktop.ini= or =Icon\r= that get committed the same way.
When the repository tracks such a file and the OS writes one into the
husk, "a tracked path exists" is true of the husk (measured, git 2.49:
=--canonical-for-identity= returned the husk).  So check 4 SKIPS every
listed path whose basename is an OS or sync-client artifact, and answers
t only for another tracked path that exists.  The list is short, closed
and compared without regard to letter case (Windows names are
case-insensitive, and so is this Mac's disk):

| name          | written by                                        |
|---------------+---------------------------------------------------|
| =.DS_Store=   | macOS Finder, in any directory it displays        |
| =._*=         | macOS AppleDouble files, on non-HFS volumes and in archives |
| =.localized=  | macOS, for folders with a localized display name  |
| =Icon\r=      | macOS custom folder icons (Finder, Dropbox, Google Drive) |
| =Thumbs.db=, =ehthumbs.db= | Windows Explorer thumbnail caches    |
| =desktop.ini= | Windows Explorer and OneDrive folder settings     |
| =.directory=  | KDE Dolphin folder settings                       |

A denylist rather than "a meaningful fraction of the tracked paths must
exist".  A fraction has to read the WHOLE index on every call, where the
denylist still stops at the first real hit (one stat for a real main
worktree).  It also refuses real main worktrees: a checkout in the
middle of a large deletion, or a sparse checkout, has most tracked paths
absent, and any threshold would be arbitrary.  The denylist removes
exactly the names that something other than git writes into arbitrary
directories, and nothing else.

Residuals, stated because they are accepted: a husk that still holds an
OLD copy of the tree passes check 4, and so does a husk into which some
other program wrote a file the repository also tracks under a name not
on the list (an editor's project settings, say).  No git-derived signal
can tell either from the real work tree.

The real main worktree =W= in those two rows is not recoverable from a
linked worktree: git records no path to it.  When =W= itself is the
checkout in view the answer is also nil — =W= is not the parent of the
common dir.  Nil over a guess.

The =D/.git= row is why the first signal alone is not enough: =D= even
passes the classifier's cheap =.git=-is-a-directory test.  The last two
rows before it are why the second signal alone is not enough: git reports
its own git directory as the "main worktree".  In the =core.worktree= row
the two signals AGREE on =D=, because git's main-worktree slot is always
the parent of the common dir and ignores =core.worktree= — while the
repository's files live in =T=.  Re-anchoring a relpath under =D= would
find nothing, or a stale copy.  Only the third check sees it: run in =D=,
=--show-toplevel= answers =T=.  (A LINKED worktree of such a repository
ignores =core.worktree= and is its own top level, measured on git 2.49.)

Check 4 reads =ls-files -z= (no quoting of unusual names) and stops at
the first listed path that exists, so a real main worktree costs one
stat.  Paths are joined to the candidate by concatenation, with file
name handlers off: a tracked name is data, and =expand-file-name= would
read a leading =~= in it as a home directory.  =file-attributes= does not
follow symlinks, so a tracked symlink counts as present even when it
dangles.

(defun workspace-bookmark--holds-tracked-file-p (dir)
  "Return non-nil when DIR holds at least one path git tracks there.

Runs `git ls-files -z' in DIR and returns t at the first listed path
that exists under DIR.  A listed path whose basename is an OS or
sync-client artifact (`workspace-bookmark--os-artifact-p') is skipped:
Finder and friends write those into any directory, the husk of a
`.git'-named git directory included.  Nil when git fails, lists
nothing, or no other listed path exists — the shape of a directory that
holds only a git directory.  Never signals."
  (let ((out (workspace-bookmark--git dir "ls-files" "-z")))
    (when out
      (condition-case nil
          (let ((root (file-name-as-directory (expand-file-name dir)))
                (file-name-handler-alist nil)
                (start 0)
                (found nil))
            (while (and (not found) (< start (length out)))
              (let* ((end (or (string-search "\0" out start) (length out)))
                     (path (substring out start end)))
                (when (and (> end start)
                           (not (workspace-bookmark--os-artifact-p path))
                           (file-attributes (concat root path)))
                  (setq found t))
                (setq start (1+ end))))
            found)
        (error nil)))))

#+begin_src emacs-lisp
(defun workspace-bookmark--canonical-checkout (dir)
  "Return the main worktree of the repository containing DIR, or nil.

The value is an absolute directory name with a trailing slash.  Two
signals must agree: the parent of the shared git directory
\(`git rev-parse --path-format=absolute --git-common-dir'), which must
be a directory named `.git', and the first, non-bare entry of `git
worktree list --porcelain'.  The candidate must then be its own top
level: `git rev-parse --show-toplevel' run in it names it, and it must
hold the work tree: at least one path git tracks exists under it (see
`workspace-bookmark--holds-tracked-file-p').  When the signals disagree
— a bare main repository, a `--separate-git-dir' layout, a submodule —
or the candidate's work tree is elsewhere (`core.worktree'), or the
candidate is a husk holding only a `.git'-named git directory whose
work tree lives elsewhere (`--separate-git-dir=<dir>/.git', or a `.git'
symlink), or any answer is unavailable, the answer is nil: no canonical
checkout is better than a guessed one.  Never signals."
  (let ((common (workspace-bookmark--git
                 dir "rev-parse" "--path-format=absolute" "--git-common-dir")))
    (when (and common
               (file-name-absolute-p common)
               (equal ".git" (file-name-nondirectory
                              (directory-file-name common)))
               (condition-case nil (file-directory-p common) (error nil)))
      (let ((candidate (file-name-directory
                        (directory-file-name (expand-file-name common))))
            (first (car (workspace-bookmark--worktree-entries dir))))
        (when (and first
                   (not (plist-get first :bare))
                   (workspace-bookmark--same-file-p (plist-get first :path)
                                                    candidate))
          (let ((top (workspace-bookmark--git
                      candidate "rev-parse" "--show-toplevel")))
            (when (and top
                       (workspace-bookmark--same-file-p top candidate)
                       (workspace-bookmark--holds-tracked-file-p candidate))
              (file-name-as-directory candidate))))))))
#+end_src

** Classification

Three symbols, tested in THIS order — ownership before structure:

1. =workspace-owned= — the checkout really lies within some registered
   workspace's =:home=, or is that home (an anchored workspace), or
   really CONTAINS that home (a workspace anchored at a subdirectory of
   the checkout).  Symbolic links confer nothing (see "Symbolic links
   are ignored" below).
2. =canonical= — =.git= is a directory.  A linked worktree's =.git= is a
   FILE (=~/.emacs.d/.git= on this machine is a 54-byte file); a main
   worktree's is a directory.  No subprocess.
3. =other= — everything else, including anything this function cannot
   test (a remote path, a non-string).

Ownership comes first because a workspace can hold a full clone rather
than a linked worktree.  That clone's =.git= is a directory, so a
structure-first test calls it =canonical= — and the safety rule would then
offer workspace A's files to a user standing in workspace B, the exact
defect this capability exists to remove.  The price is conservative: a
main worktree that sits inside a workspace home is never offered as
canonical, and the resolver reports =no-clone= instead.  Nil over a guess.

*A home inside a checkout makes that checkout workspace-owned* (user
decision, 2026-09-25).  A workspace anchored at a SUBDIRECTORY of a main
clone — =~/emacs/config=, or "my package in the monorepo" — is working
in that clone's files, so the clone is the workspace's as surely as a
clone inside its home would be.  (=workspace--new-anchor-existing= sees
no =.git= in the subdirectory and =git init=s a nested repository there,
which has no remote; so the anchored home never gives the clone's
identity itself, and only this rule keeps the clone from being offered
to another workspace.)  The test is the same containment walk with its
arguments reversed: the home's truename, or one of its ancestors, is the
checkout.

What this rule can withdraw from offer is exactly the checkouts that
contain a registered home, and nothing else: the clause is a
disjunction, so a checkout's classification changes only when some
home's truename really lies within it.  It inherits the walk's
properties: =/a/ws-old= does not contain =/a/ws=, and a symbolic link
inside the checkout that points at a home confers nothing (only the
home's own truename is walked, never a link into it).  The cost is the
conservative one again: a clone that holds a workspace home anywhere
below it is never offered, and the resolver says =no-clone=.  A
repository whose work tree is =$HOME= (a "dotfiles" repository with a
real =~/.git= directory) contains every home under =~=, so it is never
offered; that is the rule as decided, not a side effect.

Containment is tested by FILE IDENTITY, never by comparing strings.
The checkout path is truenamed, then it and each of its parent
directories in turn is compared to the home with
=workspace-bookmark--same-file-p= (device and inode; see "Same file"),
not by spelling.  A trailing slash, a =~= spelling, macOS's =/var= →
=/private/var= symlink and — the case that matters — a difference in
LETTER CASE on a case-insensitive filesystem all compare correctly, and
because whole directories are compared, =/a/ws-old= is not inside =/a/ws=.
Because only device and inode are compared, a home that is being written
to while the walk runs still compares equal to itself.  The first
implementation used =file-equal-p=, which also compares timestamps, and
under a concurrent writer it failed OPEN: see "Same file".

String comparison is rejected even after truenaming.  =file-in-directory-p=
(the first implementation) truenames both sides and then compares path
components with =string-equal=, and =file-truename= does not fold case.
On this Mac's case-insensitive disk a home registered as
=/root/wsdir/myws= for the on-disk =/Root/Wsdir/myws= is reachable —
=read-directory-name= accepts the typed case, and =workspace--make= keeps
it — and =file-in-directory-p= then says the workspace's own full clone
is NOT inside it.  Ownership-first classification turns that miss into a
=canonical= verdict for git's (on-disk-case) spelling of the clone, and
=--canonical-for-identity= would offer workspace A's clone to a user in
workspace B.  Comparing file identity says t for the same pair.

The walk stops at the filesystem root.  A path that does not exist cannot
be proven inside anything, so it is not; every caller passes existing
checkouts.

Remote paths are rejected before any filesystem call: =file-truename= on a
TRAMP name would open a connection, and a remote home cannot own a local
checkout anyway.

*Symbolic links are ignored* (user decision, 2026-09-24).  A child of a
home that is a symbolic link is not one of the workspace's checkouts —
=--home-checkouts= skips it, whatever it points to — and no link, of
any kind, makes anything =workspace-owned=.  Only real directories
count: a checkout is owned when its truename really lies inside a home,
is the home, or really contains the home's truename.  Nothing in the workspaces tooling creates links in a
home: worktrees are added with =git worktree add=, homes are scaffolded
with real directories, and an anchored home is the repository itself.

KNOWN LIMITATION — stated here because it is accepted, not fixed.  If a
user symlinks a main clone into a workspace home (=ws/A/x ->
~/src/main=) instead of adding a worktree, workspace A is editing that
clone, yet the clone is not A's: it classifies =canonical=, and
=--canonical-for-identity= may offer it to a user standing in workspace
B.  That is the defect the safety rule exists to prevent, reached
through a layout the tooling never builds.  The user's guidance is
simply: do not symlink checkouts into a workspace home; add a worktree.
The same holds for a link to a directory inside a clone, to a file
inside it, or to a directory above it.  An earlier revision owned the
targets of such links; it was removed because the rule was either too
broad (a single linked notes file silenced every bookmark into a
repository, with no diagnostic) or, once narrowed, still a partial
answer to a layout the tooling does not produce.

The flip side is conservative: because the link is not a checkout of
the workspace, a repository reachable ONLY through such a link is not
in view, and =--workspace-checkout= never answers with it.

#+begin_src emacs-lisp
(defun workspace-bookmark--path-within-p (path dir)
  "Return non-nil when PATH is DIR or lies inside it.

Both must be local and exist; DIR must be a directory.  Containment is
by file identity: PATH is truenamed, then it and each of its ancestors
is compared to DIR with `workspace-bookmark--same-file-p', so
differences of spelling — trailing slash, `~', symlinked prefixes, and
letter case on a case-insensitive filesystem — do not matter, and
neither do DIR's timestamps changing during the walk.  Never signals."
  (and (stringp path) (stringp dir)
       (not (file-remote-p path))
       (not (file-remote-p dir))
       (condition-case nil
           (let ((current (directory-file-name
                           (file-truename (expand-file-name path))))
                 (previous nil)
                 (found nil))
             (when (file-directory-p (expand-file-name dir))
               (while (and (not found) (not (equal current previous)))
                 (if (workspace-bookmark--same-file-p current dir)
                     (setq found t)
                   (setq previous current
                         current (directory-file-name
                                  (file-name-directory current))))))
             found)
         (error nil))))

(defun workspace-bookmark--owning-workspace (checkout)
  "Return the name of a registered workspace that owns CHECKOUT, or nil.

  (seq-find (lambda (name)

(defun workspace-bookmark--classify (checkout)
  "Classify CHECKOUT as `canonical', `workspace-owned' or `other'.

`workspace-owned' when a registered workspace owns CHECKOUT (see
`workspace-bookmark--owning-workspace'); otherwise `canonical' when
its `.git' is a directory (a main worktree); otherwise `other'.  Ownership is tested FIRST: a full clone
inside a workspace home, or containing one, is workspace-owned, never
canonical.  A remote or non-string CHECKOUT is `other'.

`canonical' here is structural only, and NOT sufficient to offer
CHECKOUT as a repository's canonical checkout: see
`workspace-bookmark--offerable-canonical-p'.  Never signals."
  (condition-case nil
      (cond
       ((not (and (stringp checkout) (not (file-remote-p checkout))))
        'other)
       ((workspace-bookmark--owning-workspace checkout)
        'workspace-owned)
       ((file-directory-p (expand-file-name ".git" checkout))
        'canonical)
       (t 'other))
    (error 'other)))

** A workspace's checkouts

A workspace holds its checkouts as the IMMEDIATE children of its =:home=:
=~/emacs-workspaces/<name>/<repo>/=.  Grandchildren are not searched —
this is enumeration of a known layout, not scanning.  A child that is a
symbolic link is skipped, whatever it points to: only real directories
count (see "Symbolic links are ignored" under Classification).

The home ITSELF is a checkout of the workspace too, when it is one (user
decision, 2026-09-24).  A workspace anchored at an existing repository
(=workspace-new= with a prefix argument, =workspace--new-anchor-existing=)
has that repository AS its =:home=, not as a child of it; without this
such a workspace could never resolve a bookmark into its own repository,
and the resolver would say =no-clone= while the user stands in the
clone.  The home comes first, then the children, sorted.  This does not
widen what may be offered as canonical: a home is always inside itself,
so it classifies =workspace-owned=.  A scaffolded home is a git
repository too (=git init=), usually with no remote and so no identity;
it is enumerated like any other and never matches.

*One identity, several checkouts.*  A home can hold two sibling worktrees
of one repository (=project-alpha/=, =project-zeta/=), or be a checkout
of a repository and also hold a worktree of it.
=workspace-bookmark--workspace-checkouts= returns EVERY checkout of the
identity in the home, in the order above.
=workspace-bookmark--workspace-checkout= returns a checkout only when it
is the ONLY one, and nil when there are none or several.  The first
implementation returned the alphabetically-first match, which is a
choice of branch made by =directory-files=' sort order; the consumer
could not tell, and might open the other branch's copy of the file.
Several matches is AMBIGUITY, not absence: a consumer that needs to tell
the two apart calls =--workspace-checkouts=.  How ambiguity maps onto
the resolver's outcomes is the resolver's decision, not this section's.

*Only checkout ROOTS count.*  =--home-checkouts= asks only whether a
child holds a =.git= entry, and an EMPTY =.git= directory (or any other
=.git= git does not accept) passes that test without making the child a
repository.  Git run in such a child walks up and answers for the
repository ENCLOSING it — in an anchored home, the home's own — so the
child would report the home's identity and be listed next to the home,
turning a unique answer into a false ambiguity.  A candidate is
therefore kept only when git's own top level for it IS it
(=--repo-root=, compared with =--same-file-p=).  The identity is then
read from that root, so the guard costs no extra subprocess.

Each checkout costs an identity — one =rev-parse --show-toplevel= plus
one =remote get-url= (two more when there is no =origin=) — and, because
uniqueness needs them all, every checkout of the home is asked; there is
no early stop at the first match.

#+begin_src emacs-lisp
(defun workspace-bookmark--workspace-checkouts (identity workspace-name)
  "Return every checkout of IDENTITY in WORKSPACE-NAME's home.

The candidates are those of `workspace-bookmark--home-checkouts' — the
home itself when it is a checkout, then its immediate children — and
the value keeps their order.  A candidate that is not its own checkout
root (a child whose `.git' git does not accept, which git resolves to
the repository enclosing it) is dropped.  Each is an absolute directory
name with a trailing slash.  Returns nil when IDENTITY or
WORKSPACE-NAME is nil, when the workspace is not registered, or when
nothing matches.  Never signals."
  (when (and identity workspace-name)
    (seq-filter (lambda (checkout)
                  (let ((root (workspace-bookmark--repo-root checkout)))
                    (and (workspace-bookmark--same-file-p root checkout)
                         (equal identity
                                (workspace-bookmark--root-identity root)))))
                (workspace-bookmark--home-checkouts
                 (workspace-bookmark--workspace-home workspace-name)))))
#+end_src

#+begin_src emacs-lisp
(defun workspace-bookmark--workspace-checkout (identity workspace-name)
  "Return the one checkout of IDENTITY in WORKSPACE-NAME's home, or nil.

The value is the checkout only when it is UNIQUE among
`workspace-bookmark--workspace-checkouts'.  Nil when there is none, and
nil when there are several — the home holds sibling checkouts of one
repository, and picking one would pick a branch.  Call
`workspace-bookmark--workspace-checkouts' to tell the two apart.  Also
nil when IDENTITY or WORKSPACE-NAME is nil or the workspace is not
registered.  Never signals."
  (let ((matches (workspace-bookmark--workspace-checkouts
                  identity workspace-name)))
    (and matches (null (cdr matches)) (car matches))))
#+end_src

** Checkouts in view

The checkouts in view, in order: the current workspace's checkouts (its
home, when that is a checkout, then its children; see "A workspace's
checkouts"), then those of every other registered workspace, then the
configuration repository this Emacs was loaded from (=jf/emacs-dir=).
That last one is what makes the =emacs= repository resolvable from a workspace that holds
no checkout of it: =~/.emacs.d= is itself a linked worktree, and git
expands it to its main worktree =~/emacs=.

#+begin_src emacs-lisp
(defun workspace-bookmark--checkouts-in-view ()
  "Return the checkouts in view, most relevant first, without duplicates.
The current workspace's checkouts, then every other registered
workspace's, then `jf/emacs-dir'.  A workspace's checkouts are its
home, when that is a checkout, and its home's checkout children (see
`workspace-bookmark--home-checkouts')."
  (let* ((current (workspace-bookmark--current-workspace))
         (others (remove current (workspace-bookmark--registered-names)))
         (config (bound-and-true-p jf/emacs-dir)))
    (delete-dups
     (append
      (and current
           (workspace-bookmark--home-checkouts
            (workspace-bookmark--workspace-home current)))
      (seq-mapcat (lambda (name)
                    (workspace-bookmark--home-checkouts
                     (workspace-bookmark--workspace-home name)))
                  others)
      (and (stringp config)
           (not (file-remote-p config))
           (list (file-name-as-directory (expand-file-name config))))))))
#+end_src

** The one canonical predicate

"May this directory be offered as a repository's canonical checkout?"
has exactly ONE answer in this capability, and every path that offers a
checkout as canonical — =--canonical-for-identity= (the resolver's
fallback), =workspace-bookmark-canonical-checkouts-in-view= (the public
entry point), and through it the git-worktrees repository picker — asks
it here.  Two earlier derivations disagreed: the resolver path ran
=--canonical-checkout='s four checks and then =--classify=, while the
git-worktrees picker trusted =--classify= alone, and so offered the
husk of a =.git=-named git directory while omitting the real main
worktree.

The predicate is the conjunction of both halves, and neither half is
enough alone:

- =--classify= answers =canonical= — no registered workspace owns DIR,
  and DIR's =.git= is a directory.  NECESSARY, NOT SUFFICIENT: the husk,
  a =core.worktree= directory and a bare repository stored as =D/.git=
  all pass it.
- DIR is, by file identity, what =--canonical-checkout= says is the main
  worktree of DIR's own repository — so DIR is that repository's root,
  git agrees it is the main worktree, and it holds the work tree.
  NECESSARY, NOT SUFFICIENT: a workspace's full clone passes it.

The classification is asked first because it runs no subprocess: a
workspace-owned candidate never pays for =--canonical-checkout='s four.
Nothing here catches errors: every step it composes already returns nil
(or =other=) rather than signalling.

#+begin_src emacs-lisp
(defun workspace-bookmark--offerable-canonical-p (dir)
  "Return non-nil when DIR may be offered as its repository's canonical checkout.

DIR must classify `canonical' (`workspace-bookmark--classify': no
registered workspace owns it and its `.git' is a directory) AND be, by
file identity, the main worktree `workspace-bookmark--canonical-checkout'
finds for DIR's own repository.  Neither condition is sufficient alone.
This is the ONLY test that may admit a checkout as canonical.  Never
signals."
  (and (stringp dir)
       (eq 'canonical (workspace-bookmark--classify dir))
       (workspace-bookmark--same-file-p
        dir (workspace-bookmark--canonical-checkout dir))))
#+end_src

Given some checkouts, the canonical checkouts of their repositories are
found by asking git for each repository's MAIN-WORKTREE ENTRY (the first
usable entry of =--checkouts-of=, one subprocess) and putting that
candidate to the predicate.  The candidate need not itself be in view:
that is the point of asking git.  Only the main worktree can pass,
because the predicate requires the candidate to BE the main worktree
=--canonical-checkout= names; any other entry in the candidate slot (a
linked worktree, when the main is bare or missing) fails closed.
Candidates are de-duplicated by file identity BEFORE the predicate runs,
so two checkouts of one repository cost one test, and the order of
first appearance is kept.

#+begin_src emacs-lisp
(defun workspace-bookmark--canonical-checkouts-among (checkouts)
  "Return the canonical checkouts of the repositories of CHECKOUTS.

For each of CHECKOUTS, in order, the main-worktree entry git lists for
its repository is a candidate; candidates are de-duplicated by file
identity (first occurrence kept) and only those that pass
`workspace-bookmark--offerable-canonical-p' are returned.  Each is an
absolute directory name with a trailing slash.  Never signals."
  (seq-filter
   #'workspace-bookmark--offerable-canonical-p
   (seq-uniq (delq nil (mapcar (lambda (checkout)
                                 (car (workspace-bookmark--checkouts-of
                                       checkout)))
                               checkouts))
             #'workspace-bookmark--same-file-p)))
#+end_src

** The safety rule, and ambiguity

=workspace-bookmark--canonical-checkouts-for-identity= finds every
in-view checkout of the identity and returns every DISTINCT canonical
checkout of their repositories.  If none survives, the answer is nil,
which the resolver maps to =no-clone= — never "the closest thing in
view".

*Two separate main clones of one identity are AMBIGUOUS* (user decision,
2026-09-25).  An old standalone clone next to a newer one, or
=~/.emacs.d= as its own clone next to =~/emacs=, are each a legitimate
main worktree that no workspace owns, and they can be on different
branches.  The first implementation returned the first one found, so
the answer depended on which workspace was current and then on registry
order, and the consumer could not tell a choice had been made.
=workspace-bookmark--canonical-for-identity= therefore returns a
checkout only when it is the ONLY distinct one, and nil when there are
none or several — the same shape as =--workspace-checkout(s)=.  A
consumer that must tell "none" from "several" calls the plural.  How
ambiguity maps onto the resolver's outcomes is the resolver's decision,
not this section's.  Two worktrees of ONE repository in view are not
ambiguous: they share one main worktree, which is counted once.

The plural asks every in-view checkout for its identity, because
uniqueness needs them all; there is no early stop at the first match.

#+begin_src emacs-lisp
(defun workspace-bookmark--canonical-checkouts-for-identity (identity)
  "Return every distinct canonical checkout of IDENTITY, or nil.

Searches the checkouts in view (`workspace-bookmark--checkouts-in-view')
for those whose identity is IDENTITY, and returns the canonical
checkouts of their repositories that pass
`workspace-bookmark--offerable-canonical-p', de-duplicated by file
identity, in order of first appearance.  A workspace-owned or `other'
checkout is never returned.  Nil when IDENTITY is nil, when no checkout
of it is in view, or when none passes.  Never signals."
  (when identity
    (workspace-bookmark--canonical-checkouts-among
     (seq-filter (lambda (checkout)
                   (equal identity (workspace-bookmark--identity checkout)))
                 (workspace-bookmark--checkouts-in-view)))))

(defun workspace-bookmark--canonical-for-identity (identity)
  "Return THE canonical checkout of IDENTITY, or nil.

The value is the checkout only when it is UNIQUE among
`workspace-bookmark--canonical-checkouts-for-identity'.  Nil when there
is none, and nil when there are several — separate main clones of one
repository, and picking one would pick by workspace or registry order.
Call the plural to tell the two apart.  A workspace-owned or `other'
checkout is never returned.  Never signals."
  (let ((all (workspace-bookmark--canonical-checkouts-for-identity identity)))
    (and all (null (cdr all)) (car all))))
#+end_src

** Cross-module interface: the canonical checkouts in view

=workspace-bookmark-canonical-checkouts-in-view= is this module's ONE
public discovery function, and a CROSS-MODULE INTERFACE: the
git-worktrees repository picker (=config/workspaces/git-worktrees.org=,
=jf/workspace--worktree-git-derived-candidates= and
=jf/workspace--worktree-canonical-only=) calls it, and it calls nothing
else in this module.  Everything with a =--= in its name stays private
and may change freely.

STABILITY PROMISE.  The name, the calling convention and the meaning
below are a contract.  Changing any of them means changing
=git-worktrees.org= in the same commit.  The consumer guards the call
with =fboundp= at CALL time and never =require=s this module (a
magit-dependent module must not depend on a bookmark module), so a
rename would not fail loudly: the picker would silently lose its
git-derived source.  The tripwire is =config/workspaces/test/git-worktrees-spec.el=
§ "git-derived repo candidates", which loads this module for real.

- =(workspace-bookmark-canonical-checkouts-in-view)= — the canonical
  checkouts of the repositories of the checkouts in view
  (=--checkouts-in-view=), in view order.
- =(workspace-bookmark-canonical-checkouts-in-view CHECKOUTS)= — the
  same for the list CHECKOUTS instead of the checkouts in view.
  =CHECKOUTS= given as nil means NONE, not "the default": the result is
  nil.  (git-worktrees passes magit's repository list here, so that
  magit's candidates are admitted by the same predicate.)
- Every element passed =workspace-bookmark--offerable-canonical-p=: a
  repository's main worktree, owned by no workspace, and holding its
  work tree.  Never a workspace's checkout, a linked worktree, a husk,
  or a =core.worktree= directory.
- Absolute directory names with a trailing slash, as git spells them;
  no two name the same directory.
- Never signals in normal operation: every step returns nil on failure.
  The consumer still wraps the call in an error barrier, because a bug
  here must not break worktree creation.

#+begin_src emacs-lisp
(cl-defun workspace-bookmark-canonical-checkouts-in-view
    (&optional (checkouts nil checkouts-given))
  "Return the canonical checkouts of the repositories in view.

With no argument, the repositories in view are those of the checkouts
in view (`workspace-bookmark--checkouts-in-view'): the current
workspace's, then every other registered workspace's, then
`jf/emacs-dir'.  With CHECKOUTS, a list of directories, they are the
repositories of CHECKOUTS instead; CHECKOUTS nil yields nil.

Each element is its repository's main worktree and passed
`workspace-bookmark--offerable-canonical-p': never a workspace-owned
checkout, a linked worktree, or a directory that is not a main
worktree.  The value is in order of first appearance, de-duplicated by
file identity, each an absolute directory name with a trailing slash.

This is a CROSS-MODULE INTERFACE, called from git-worktrees.el behind a
call-time `fboundp' guard; its name, calling convention and meaning are
stable.  Never signals in normal operation."
  (workspace-bookmark--canonical-checkouts-among
   (if checkouts-given
       checkouts
     (workspace-bookmark--checkouts-in-view))))
#+end_src

* Advice installation

Installation AND matching removal are both defined so the module can be
reloaded during development without stacking advice.  =advice-add= does
not duplicate an advice that names the same function symbol, so
=workspace-bookmark-install-advice= is idempotent; the explicit removal
exists for =M-x workspace-bookmark-remove-advice= during development and
for tests that need stock bookmark behaviour.

#+begin_src emacs-lisp
(defun workspace-bookmark-install-advice ()
  "Install the two portable-bookmark advice seams.  Idempotent."
  (interactive)
  (advice-add 'bookmark-make-record :filter-return
              #'workspace-bookmark--stamp-record)
  (advice-add 'bookmark-handle-bookmark :around
              #'workspace-bookmark--handle-bookmark-advice))

(defun workspace-bookmark-remove-advice ()
  "Remove the two portable-bookmark advice seams, restoring stock behaviour."
  (interactive)
  (advice-remove 'bookmark-make-record
                 #'workspace-bookmark--stamp-record)
  (advice-remove 'bookmark-handle-bookmark
                 #'workspace-bookmark--handle-bookmark-advice))

(workspace-bookmark-install-advice)
#+end_src

=git-worktrees.el= → =workspace-git-worktrees=).  The prefix keeps the
