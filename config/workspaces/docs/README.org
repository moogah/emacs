#+title: Workspaces

Named tab-based workspaces with per-workspace named layouts, a
filesystem-anchored home directory, recent-layout pointer,
per-workspace buffer membership scoping (via [[https://github.com/florommel/bufferlo][bufferlo]]), and
per-machine persistence.  Each workspace is bound 1:1 to a tab and to
a =:home= directory on disk that holds =home.org= (the dashboard /
display-name source) and =sessions/= (gptel session files).

* Concepts

| Term          | What it is                                                  |
|---------------+-------------------------------------------------------------|
| /workspace/   | A named user-facing context; one tab in =tab-bar-mode=      |
| /home/        | The workspace's filesystem anchor (absolute path)           |
| /layout/      | A named, restorable window configuration inside a workspace |
| /home layout/ | A reserved layout-group name; every workspace has one       |
| /membership/  | The set of buffers visible to the current workspace's tab   |

A workspace is bound 1:1 to a tab, tagged via the =workspace-name=
tab parameter, and anchored to a =:home= directory on disk.  After a
restart a workspace is in the registry but has no tab until it is
restored (see *Restore*).  The
registry /name/ of a workspace equals the basename of its =:home=
(e.g. =~/emacs-workspaces/notes/= → =notes=).  The /display name/
defaults to the registry name and may be overridden by a =#+TITLE:=
keyword in =<home>/home.org=; editing =#+TITLE:= never changes the
registry name or invalidates the persistence file.

Layouts are window configurations stored under the workspace; they
are named, with no upper bound.  =home= is the reserved layout-group
name (distinct from the =:home= directory): it is built once per
workspace via the =workspace-home-builder= function.

* Home directory

Every workspace has an absolute =:home= path.  By default, new
workspaces are scaffolded under =~/emacs-workspaces/<name>/=;
override =workspaces-default-parent-directory= to point elsewhere.

The home directory contains:

- =home.org= — your dashboard.  The package writes it exactly once
  at scaffold time and never modifies it after that.  Add whatever
  you like (links, TODOs, embedded session listings).  A
  =#+TITLE:= keyword here overrides the workspace's display name
  without changing its registry name.
- =sessions/= — where new gptel persistent sessions land when this
  workspace is active (see *gptel sessions*).

The package does not auto-render =sessions/= contents back into
=home.org=.  If you want a listing, add it manually; =sessions/=
on disk is the source of truth.

* Creating workspaces

=workspace-new= (=C-x w n=) has two flows controlled by the prefix
argument:

Workspace homes must be local.  Remote (TRAMP) directories are not
supported as workspace homes: =workspace-new= (either flow) and
=workspace-re-anchor= refuse one with a =user-error= naming it, before
the command touches the filesystem.  A remote home already in the state
file (saved before this rule, or written by hand) is loaded /broken/
without being contacted, with one warning naming it (see *Broken
workspaces*).

Every command that registers a workspace refuses a name that is already
registered — including a broken workspace's — because the registry is
keyed by name and registering would replace that workspace, losing its
saved layouts.

** No prefix arg — scaffold a fresh directory

=workspace-new NAME= scaffolds a new directory at
=(expand-file-name NAME workspaces-default-parent-directory)=.  The
scaffold pipeline runs five stages in order: =make-directory=,
=git init=, write =home.org= skeleton, =make-directory sessions/=
(created /empty/), then =git add . && git commit -m "Initial
workspace"=.  =sessions/= is no longer seeded with an eager
=<date>-initial.org= file; it is populated on demand or at birth by
registered integrations (see *Integration registry* below — the
gptel integration's =:on-create= handler writes a real scoped
session, which lands untracked after the Initial-workspace commit).
Only after scaffolding succeeds is the workspace registered, a tab
created, =workspace-home-builder= called, and the integration
=:on-create= handlers dispatched.

If a workspace named NAME is already registered (anchored elsewhere,
or broken), =workspace-new= refuses with a =user-error= naming its home
instead of replacing it; for a broken one the message points at
=workspace-re-anchor= and =workspace-purge=.  If the target directory
already exists, =workspace-new= signals a hard =user-error= and tells
you to use the prefix-arg form to anchor an existing directory.  Scaffold failures (=git= missing, permission
denied) propagate verbatim; partial filesystem state is left in
place for manual inspection (design.md §D2 — auto-cleanup of a
typo'd path would risk =rm -rf= on user data).

** =C-u= — anchor an existing directory

=C-u M-x workspace-new= ignores the name prompt and instead asks for
an existing directory.  The new workspace's name is derived from the
directory's basename.  Three sub-cases by directory state:

1. *Git repo with =home.org= already present* — register only.  No
   scaffolding, no git ops; we never touch a repo we did not create
   and never overwrite a user-authored =home.org=.
2. *Git repo, no =home.org=* — scaffold files only (skip =git init=
   and the initial commit).  =home.org= and =sessions/= land in your
   repo; you stage and commit them when you choose.
3. *Not a git repo* — full scaffold (mkdir is idempotent, =git
   init=, files, initial commit), same as the default-path branch.

A double-registration guard refuses to anchor a directory that is
already a registered workspace's =:home=.  Directories are compared by
device and inode, not by spelling, so two spellings of the same
directory (a trailing slash, a =~= prefix, a symlinked parent, a
different letter case on a case-insensitive disk) are recognised as
one.  That comparison never opens a remote connection and cannot tell
two remote spellings apart (another mount path of the same remote
directory would register it twice), which is why remote homes are
refused outright (above).

A second guard, shared with the no-prefix flow, refuses to anchor a
directory whose basename is already a registered workspace's name —
=~/b/proj= while "proj" lives at =~/a/proj= — because the workspace name
IS the basename, and anchoring would replace the existing workspace
(losing its saved layouts).  The error names the existing workspace's
home; rename one of the directories to anchor both.

* Deleting and purging workspaces

Two commands handle workspace removal, with deliberately split
semantics.

** =workspace-delete= (=C-x w D=) — unregister only

Removes the workspace from the registry, closes its tab, and flushes
persistence.  The =:home= directory and all its contents
(including =.git/=, =home.org=, =sessions/=) are left on disk
untouched.  This is the safe default: a =kill-buffer=-style mental
model gets non-destructive removal.

The "delete then re-anchor later" workflow works precisely because
=workspace-delete= leaves the files alone — invoke =C-u M-x
workspace-new= and point it at the dir to bring it back.

** =workspace-purge= (=C-x w P=) — destructive

Unregisters the workspace and recursively deletes the =:home=
directory after a =yes-or-no-p= confirmation showing the absolute
path.

A scope safeguard refuses to operate when =:home= is not strictly
below =workspaces-default-parent-directory= unless you supply a
prefix argument.  This protects anchored existing projects (e.g.
=~/code/myproj/=) from accidental destruction: you must invoke =C-u
M-x workspace-purge= to opt in to deleting a dir outside the default
parent.  The default parent ITSELF (in any spelling) is outside too: a
workspace anchored at =~/emacs-workspaces/= would otherwise be purged,
with every workspace below it, after a single "yes".  Strictly inside
the default parent the safeguard is silent and only =yes-or-no-p=
guards the delete.

Order is deliberate: unregister first, =delete-directory= second.
If the filesystem delete errors (permission denied, file busy), the
registry is already clean, so the workspace appears removed from
your perspective; leftover state is inspectable out-of-band.

Both commands also operate on broken-state workspaces (see *Broken
workspaces*).  Purge skips the filesystem step when =:home= is
already missing on disk — registry cleanup still proceeds.

* Broken workspaces

A workspace becomes /broken/ at load time when the persistence
loader sees its =:home= is no longer a directory on disk (the
directory was moved, deleted, or renamed out-of-band while Emacs was
down).  The loader tags the in-memory entry with a runtime-only
=:broken= flag and emits a =*Messages*= notice naming the workspace
and its missing =:home=.

A workspace whose saved =:home= is remote (TRAMP) is also loaded
broken, but WITHOUT any filesystem call on the home (checking it would
open a connection at startup), and with one warning naming it.  Remote
homes are not supported; the entry is kept so its layouts survive the
next save.  Re-anchor it to a local directory, or =workspace-delete=
it.

The =:broken= tag never persists to disk: it lives on the registry
plist at runtime only, recomputed on every load from the current
state of the filesystem.  No surgery on the persistence file is
needed; just fix the dir.

Three operations are /allowed/ on a broken workspace:

- =workspace-re-anchor= (=C-x w R=) — point the registry entry at
  a new home directory.  Prompts for the workspace name and the
  new path; the path must exist and be a directory.  If the new
  basename differs from the registry key, the registry entry is
  renamed in place (and the live tab relabelled) to honour the
  invariant that the registry name equals the basename.  The new
  path must not be another workspace's home, in any spelling (a
  symlink or a different letter case): two workspaces never share
  one directory.
- =workspace-purge= (=C-x w P=) — remove the registry entry.  The
  filesystem step is skipped automatically when =:home= is already
  missing.
- =workspace-delete= (=C-x w D=) — also removes the registry
  entry; equivalent to purge for broken entries since there is no
  directory to delete.

Two operations are /refused/ on a broken workspace, with an error
message naming both remediation commands:

- =workspace-switch= (=C-x w s=)
- =workspace-restore= (=C-x w o=)

Routing concerns also honour broken state: gptel session creation
falls through to the global default rather than re-materialising the
missing directory (see *gptel sessions*).

* gptel sessions

When a workspace owns the current tab and the =workspaces= feature
is loaded, =jf/gptel-persistent-session= writes new session
directories under that workspace's =<:home>/sessions/=.  When no
workspace owns the current tab, the active workspace is broken, or
its =sessions/= directory has been removed out-of-band, creation
falls through to the global =jf/gptel-sessions-directory=.

Two user-facing commands:

- =M-x jf/gptel-persistent-session= — the default flow.  Routes
  to the active workspace's =sessions/= when one applies; otherwise
  global.  Its existing =C-u= prefix prompts for a preset (the
  prefix is already spoken for in the per-session UX), so it is
  /not/ the global-override knob.
- =M-x jf/gptel-persistent-session-global= — the
  escape-hatch.  Forces the global =jf/gptel-sessions-directory=
  unconditionally, even when a workspace is active.  Use this when
  you explicitly want a session outside any workspace.

The =sessions/= directory contents are the source of truth.  The
workspaces package does not auto-render a listing into =home.org=;
if you want one, write it by hand or via a custom
=workspace-home-builder=.

The integration is one-way: workspaces never references gptel;
gptel-side code reaches into workspaces behind a =(featurep
'workspaces)= + =fboundp= guard.  The published consult function is
=workspace-sessions-dir= (nil on the three no-route conditions:
off-workspace, broken workspace, missing =sessions/= dir).

* The =C-x w= menu

=C-x w= opens =workspace-menu=, a single context-aware transient that
is the front door to every workspace command.  The menu inspects the
current tab and shows only the groups that apply, so its surface
changes with context:

- *No current workspace* — only the *Entry* group is shown: =New=
  (=n=), =Switch= (=s=), =Restore= (=o=).  These are the ways /into/ a
  workspace; nothing operational applies when you are not in one.
- *In a healthy workspace* — the full surface: *Entry* plus *Layouts
  + State* (switch/save layout, recent layout, save/revert workspace),
  *Manage / Recover* (delete, purge, re-anchor, remove buffer), and a
  dynamically-populated *Integrations* group (see *Integration
  registry* below).
- *In a broken workspace* — recovery only: the *Entry* and *Manage /
  Recover* groups are shown (the latter offering re-anchor, purge, and
  delete), while the *Layouts + State* and *Integrations* groups are
  suppressed.  You cannot operate a workspace whose =:home= is missing;
  you can only repair or remove it.

=C-x w= now /opens the menu/; the old individual =C-x w <key>= chords
(=C-x w n=, =C-x w s=, …) are retired.  Every command remains reachable
through the menu — where the old mnemonics survive as the menu keys —
and via =M-x=.  Bracketed bindings shown in the *Command reference*
table below denote the in-menu key, not a standalone global chord.

* Integration registry

External subsystems plug into workspace creation through a small
registry rather than by being hard-wired into the package.  This keeps
the dependency direction one-way: workspaces names no integration, and
each integration reaches in only through the published
=workspace-register-integration= entry point.

An integration registers itself by calling:

#+begin_src emacs-lisp
(workspace-register-integration ID
  :label    "Display name"
  :on-create #'handler        ; optional — fires at workspace birth
  :menu      (cons "g" #'cmd)) ; optional — on-demand menu entry
#+end_src

At least one of =:on-create= or =:menu= must be supplied (a
registration with neither surface is inert and signals a =user-error=).
Registration order is significant: both =:on-create= dispatch and
=Integrations= menu rendering walk the registry in registration order,
and re-registering an existing ID updates it in place.

- =:on-create= — a non-interactive handler that auto-fires once when a
  workspace is born (any of the three creation contexts: a fresh
  scaffold, an anchored-and-scaffolded directory, or an
  anchored-existing directory).  Workspaces pushes an *anchor payload*
  — a flat plist of =:name=, =:home=, =:sessions-dir=, and =:context=
  — to each handler.  The handler reports its result as =ok=,
  =skipped=, or =(failed . REASON)=.  Failures are *visible but
  non-fatal*: a =(failed . REASON)= outcome (or a signalled error,
  which normalizes to one) emits a =*Messages*= notice naming the
  integration and reason, but *never aborts workspace creation*.
- =:menu= — an optional =(KEY . COMMAND)= pair contributing an entry to
  the menu's *Integrations* group, invoked on demand in a healthy
  workspace.

*gptel-session is the first real client.*  Its =:on-create= handler
builds a real scoped gptel session under the new workspace's
=sessions/= directory at birth, and its =:menu= entry =g= ("gptel
session") adds a further scoped session on demand from the menu.  The
handler lives under =config/gptel/= and attaches itself via
=workspace-register-integration=; the workspaces package itself names
no gptel symbol.

* Public read API

Programs read workspaces by name, without needing a selected frame or a
current tab, through five functions.  Each one only reads: it changes no
frame, tab, window, buffer or registry entry, and never writes the state
file.

| Function                                      | Returns                                                                          |
|-----------------------------------------------+----------------------------------------------------------------------------------|
| =(workspace-names)=                           | The registered workspace names                                                   |
| =(workspace-get NAME)=                        | NAME's workspace plist (a top-level copy; treat its values as read-only), or nil |
| =(workspace-layouts NAME &key origin source)= | One =(:name :origin :description :source)= plist per layout, in group order      |
| =(workspace-for-directory DIR)=               | The name of the workspace whose home contains DIR (deepest home wins), or nil    |
| =(workspace-layout-on-screen-p NAME LAYOUT)=  | Non-nil when LAYOUT is NAME's recent layout and NAME has a tab in any frame      |

- =workspace-layouts= reads each layout's origin, description and
  source; a layout with no recorded origin is the user's (=user=).
  =:origin= filters with =eq= (=user= or =agent=), =:source= with
  =equal=.  An unknown NAME has no layouts.
- =workspace-for-directory= judges containment by file identity, so a
  trailing slash, =~= or a symlinked spelling of DIR finds the same
  workspace.  A remote or missing home owns nothing, and a remote home is
  never contacted.
- =workspace-layout-on-screen-p= counts a tab that is open but not the
  current one, in any live frame.

org-graph reads the workspace homes it indexes through =workspace-names=
and =workspace-get=.

* Programmatic layouts

A program — an agent tool, an integration — gives a workspace a layout
or takes one away with two functions.  They address the workspace by
name, work whether or not it has a tab, change only its registry entry,
and write the state file once.  They never switch layouts or touch a
frame, tab, window or buffer, so the user sees nothing until they choose
to switch to the new layout.

| Function                                                     | What it does                                                         |
|--------------------------------------------------------------+----------------------------------------------------------------------|
| =(workspace-add-layout WS-NAME LAYOUT-NAME STATE &rest META)= | Store window-state STATE as layout LAYOUT-NAME of WS-NAME            |
| =(workspace-remove-layout WS-NAME LAYOUT-NAME)=               | Remove layout LAYOUT-NAME from WS-NAME                               |

META is keyword arguments: =:origin= (=agent= by default, or =user=),
=:description= and =:source=.  Adding never moves the workspace's recent
layout pointer.  Removing moves it only when it named the removed layout
(or was unset), the same way =workspace-delete-layout= does: to the
first remaining layout, else =home=.

Four rules keep a program's writes from fighting the user's:

- *R1 — added content is the baseline.*  An added layout holds STATE as
  its =:saved-state= with no =:working-state=.  Whatever the user
  changes while viewing it autosaves into =:working-state= as usual, so
  =workspace-revert= brings back the layout as the program added it.
- *R2 — user layouts are off limits.*  A program never replaces or
  removes a layout whose origin is =user=.  A layout with no recorded
  origin, which includes every layout saved before origins existed, is
  the user's.  The program must pick another name.
- *R3 — not while it is on screen.*  A program may replace or remove an
  =agent= layout, discarding any drift on it, unless that layout is on
  screen (=workspace-layout-on-screen-p=: it is the workspace's recent
  layout and the workspace has a tab open in some frame).  An open tab
  restores its own window configuration, and the next autosave would
  hide the replacement under =:working-state=, so the write is refused
  rather than silently lost.
- *R4 — an explicit save takes ownership.*  Saving over an =agent= layout
  with =workspace-save= or =workspace-save-layout= makes it the user's;
  from then on R2 protects it.

A refused write signals a =user-error= and changes nothing.  Agent tools
pass the message on unchanged:

| Refusal                       | Message (for layout =L= of workspace =W=)                                                                              |
|-------------------------------+--------------------------------------------------------------------------------------------------------------------|
| Reserved name                 | =Layout "home" is reserved for the workspace's home layout; a program cannot add, replace or remove it=              |
| R2: the user's layout         | =Layout "L" in workspace "W" belongs to the user; a program cannot replace or remove it (to add a layout, use another name)= |
| R3: on screen                 | =Layout "L" in workspace "W" is on screen; it cannot be replaced or removed while the user is looking at it=        |
| Unregistered workspace        | =No workspace named "W"=                                                                                           |

Removing a layout =W= does not have is not a refusal: it succeeds,
changes nothing and writes nothing, so an agent's cleanup can run again
safely (=workspace-delete-layout=, the interactive command, still
reports an unknown name).

* Agent tools

=agent-tools.el= gives gptel agents two tools, in the =workspaces=
category, over the programmatic layout functions above.  Both are
synchronous.  They register when gptel loads (=with-eval-after-load
'gptel=, so the order in which workspaces and gptel load does not
matter), and gptel stays optional: without it the module only defines
functions.  Dropping its line from =workspaces.el= removes the tools and
nothing else.

| Tool                      | Arguments                                                                              |
|---------------------------+----------------------------------------------------------------------------------------|
| =workspace_add_layout=    | =workspace= or =directory=, =layout_name=, =split=, =panes=, =description?=, =source?= |
| =workspace_remove_layout= | =workspace= or =directory=, =layout_name=                                              |

- *Which workspace.*  Exactly one of =workspace= (a registered name) or
  =directory= (an absolute directory inside a workspace's home, e.g. a
  repository root; the deepest home containing it wins, as
  =workspace-for-directory= decides).
- *The layout.*  =split= is ="columns"= (side by side) or ="rows"=
  (stacked).  =panes= is a non-empty array whose members are either
  ={"file": PATH, "line": N}= (=line= optional, 1-based) or a nested
  ={"split": …, "panes": […]}=, to any depth.  Panes in one split share
  its space evenly.  The tool stores this as a recipe layout with origin
  =agent=, =description= and =source= as its metadata.
- *Paths.*  A relative =file= is taken relative to =directory= when the
  workspace was found by one, and relative to the workspace's home when
  it was named; an absolute one is kept, and a =~= is expanded.  A
  =directory= that names a file is refused.  Every file must exist and not be
  a directory.  Nothing is opened: the files are visited only when the
  user switches to the layout.
- *Errors.*  Everything is checked before anything is written.  A bad
  argument (both or neither of =workspace= / =directory=, an unknown
  workspace or directory, a bad =split=, an empty or malformed pane, an
  unknown pane key, a non-positive =line=, a missing file) and every
  refusal in the table above come back to the agent as an error whose
  text names the problem — the pane by its position (=panes[1].panes[0]=),
  the file by name — and the workspace is left as it was.  On success
  the tool returns a one-line confirmation.
- *What the user sees.*  Nothing, until they switch to the layout: the
  tools change no frame, tab, window or buffer.

*Convention: a layout per orchestrator ask.*  An orchestrator that asks
the user a decision names the layout =ask/<ask-id>=, sets =source= to the
ask id, puts the ask file beside the files it refers to, and removes the
layout with =workspace_remove_layout= when the ask is closed.  The
add tool's description tells the model this.

* Command reference

Every command is reached from the =C-x w= menu (or by =M-x=).  The
*Menu key* column is the key pressed /inside/ the menu, not a global
chord.

| Menu key | Command                              | What it does                                                 |
|----------+--------------------------------------+--------------------------------------------------------------|
| =n=      | =workspace-new=                      | Scaffold a new workspace; =C-u= to anchor an existing dir    |
| =s=      | =workspace-switch=                   | Select an existing workspace's tab (refuses broken)          |
| =o=      | =workspace-restore=                  | Materialize a saved workspace into a tab (refuses broken)    |
| =S=      | =workspace-save=                     | Capture the current frame into =:saved-state= and flush      |
| =r=      | =workspace-revert=                   | Discard =:working-state=, restore last =:saved-state=        |
| =b=      | =workspace-remove-buffer=            | Remove a buffer from the current workspace's membership      |
| =l=      | =workspace-switch-layout=            | Switch to a named layout in the current workspace            |
| =L=      | =workspace-save-layout=              | Save current window config as a named layout                 |
| =T=      | =workspace-switch-to-recent-layout=  | Jump to the workspace's most recently activated layout       |
| =R=      | =workspace-re-anchor=                | Point a broken workspace at a new =:home=                    |
| =D=      | =workspace-delete=                   | Unregister a workspace; leave its home directory on disk     |
| =P=      | =workspace-purge=                    | Unregister AND recursively delete the home directory         |

The layout-scoped delete command (=workspace-delete-layout=, formerly
on the =D= chord) is still available via =M-x= but holds no menu key
— =D= now flags the destructive workspace-level delete.  The
recent-layout pointer was moved from =R= to =T= so =R= could host the
broken-state recovery command (mnemonic: re-anchor).

* Customization

=workspace-home-builder= — the function called to build a freshly
created workspace's =home= layout.  Called with one argument
(WORKSPACE-NAME) in the context of the new workspace.  The default
=workspace-default-home-builder= opens =<:home>/home.org= in a
single window.  Example override that opens an index file instead:

#+begin_src emacs-lisp
(setq workspace-home-builder
      (lambda (_name)
        (delete-other-windows)
        (find-file "~/notes/index.org")))
#+end_src

=workspaces-default-parent-directory= — directory under which
=workspace-new= scaffolds new workspace homes.  Default:
=~/emacs-workspaces/=.  Also acts as the scope-safeguard boundary
for =workspace-purge= (purges of this dir itself, or outside it,
require =C-u=).

=workspace-anti-save-predicates= — list of nullary predicate functions
consulted before the tab-switch, idle-timer and =kill-emacs= autosaves.
If any predicate returns non-nil the capture is silently skipped (at
=kill-emacs= the registry is still written; see *Save triggers*).  The
explicit =workspace-save= command never consults this list, so a
misconfigured predicate cannot trap a deliberate save gesture.

Defaults:

- =active-minibuffer-window= (built-in) — skip while a minibuffer is
  active.
- =workspace--backtrace-visible-p= — skip when a =*Backtrace*= window
  is showing on the current frame.

Example: add a "skip during isearch" predicate:

#+begin_src emacs-lisp
(add-to-list 'workspace-anti-save-predicates
             (lambda () (bound-and-true-p isearch-mode)))
#+end_src

* Persistence

Workspaces persist to a per-machine path keyed by =jf/machine-role=:

#+begin_src
state/workspaces/<machine-role>/workspaces.eld
#+end_src

The path is relative to the configuration checkout (=jf/emacs-dir=);
=default= stands in for =<machine-role>= when =jf/machine-role= is
unset.  Like everything under =state/=, the file is ignored by git.

The file is plain elisp (readable with =read=).  The package writes
=:version 4= and reads versions 3 and 4.  A v3 file loads without
loss and is rewritten as v4 on the next save.  The package does /not/
read v1, v2 or any later version; if such a file exists, the reader
emits a =*Messages*= notice naming the file, the version it found and
the versions it reads, and Emacs starts with no workspaces.  See
*State format is pre-alpha* below.

** Schema v4

v4 adds no slot to v3.  What changes is what a layout may hold:

- a /recipe/ as its =:saved-state= (a list =(:recipe . SLOTS)= whose =cdr= is the plist =:split DIR :panes PANES=,
  describing panes by file rather than capturing a window tree) in
  place of a captured window-state;
- layout metadata in its =:etc= alist: =origin= (=user= or =agent=),
  =description= and =source=.

Both ride inside =:layout-groups=, so a v3 file is exactly a v4 file
with no recipes and no metadata: each of its layouts reads as the
user's, with a captured window-state.  The version still bumps so that
code older than recipes ignores a v4 file (with its version notice)
instead of handing a recipe to =window-state-put=.  See *State format
is pre-alpha* for what that older code then does to the file.

v4 keeps everything v3 introduced.  v3 records each workspace with
its required =:home= absolute path — v2 had no =:home= slot and
treated workspaces as floating contexts keyed by name only.  v3 also enforces absolute =:home= paths at
deserialize time: entries with a relative =:home= are skipped and a
=*Messages*= notice is emitted for each.  Relative paths cannot be
disambiguated (the workspace might restore in a different working
directory on a different machine) so dropping them is safer than
guessing.

=:broken= is a /runtime-only/ tag managed by helpers
(=workspace--mark-broken=, =workspace--clear-broken=); it lives on the
registry plist only and
is stripped at the persistence boundary so it never appears in
=workspaces.eld=.  This means the on-disk format does not need to
encode transient state, and a missing-home entry recomputes its
broken status on every load against the current state of the
filesystem.

** Two-state layouts

Each layout holds two window-state slots and an open-ended =:etc=
alist:

- =:saved-state= — written by explicit saves (=workspace-save=,
  =workspace-save-layout NAME= and =workspace--capture-home-layout=,
  the =workspace-new= home stamp, all through
  =workspace--autosave-current-layout=) and by =workspace-add-layout=
  (see *Programmatic layouts*).  This is the user's "I mean this
  configuration" baseline, or the program's for an added layout.
  Authoritative across restarts.  =workspace-add-layout= stores
  whatever STATE it is given; only the agent tool passes it a recipe
  (below).
- =:working-state= — written only by autosaves (leaving a workspace's
  tab, switching layouts within a workspace, the idle timer,
  =kill-emacs=).  May be nil.  Captures drift
  between explicit saves so a restart lands the user back where they
  actually were.
- =:etc= — alist for forward-compatible extension data.  Replaces
  the legacy =:git-state= placeholder.  Today it holds the layout
  metadata: =origin= (=user= or =agent=; absent reads as =user=),
  =description= and =source=, written only by
  =workspace--layout-with-metadata= (see *Programmatic layouts*).
  Other entries are kept as they are.

Autosaves /never/ write =:saved-state=; explicit saves /always/
clear =:working-state=.  This pair of invariants means the user's
deliberate save can never be silently overwritten by transient or
post-debug frame state, and a fresh explicit save becomes a clean
baseline.

=:saved-state= may also hold a /recipe/ instead of a captured
window-state: a declarative tree of file panes, split into columns or
rows (nested to any depth, panes sharing each split evenly), each
pane optionally at a line —
=(:recipe :split columns :panes ((:file "/abs/a.org" :line 40) (:file "/abs/b.md")))=.
Storing a recipe opens nothing.  It becomes windows only when the
layout is applied (switching to it, restoring the workspace or
reverting), at which point each pane's file is visited and point put
on its line; a pane whose file no longer exists shows a placeholder
buffer naming the missing path, and the other panes are built as
usual.  Once you have looked at the layout, autosaves capture what is
on screen into =:working-state= as usual, while the recipe stays the
=:saved-state=: =workspace-revert= rebuilds the layout from the
recipe against the files as they are now.  An explicit save replaces
the recipe with a captured snapshot.

** What persists

- Workspace names, =:home= absolute paths, and recent-layout
  pointers.
- Each workspace's layouts (the two window-state slots above; see
  *Buffer reincarnation* for how individual buffers come back).
- Each workspace's list of /file/ buffers (=:buffer-files=), taken from
  its membership at each explicit =workspace-save=.  Nothing reads the
  list back: restoring a workspace brings back the buffers in its
  layout's windows (see *Buffer reincarnation*), not this list.
  Non-file buffers (=*Messages*=, =magit-status=, =eshell=) participate
  in membership in-session only, and reincarnate from the saved
  window-state via their major modes' bookmark handlers.

** Save triggers

Every write is synchronous: each trigger below writes the whole
registry to disk at once, through =workspace--write-state= (normally
via =workspace--flush-state=; the =kill-emacs= write calls it
directly).  There is no debounce and no deferred write: every write
happens inside the trigger that causes it, and there is no option to
delay it.

Explicit saves (write =:saved-state=, clear =:working-state=):

- =workspace-save= (=C-x w S=).  Captures the current frame into the
  recent layout's =:saved-state=, clears its =:working-state=, syncs the
  file list, and writes.  Never consults
  =workspace-anti-save-predicates=.
- =workspace-save-layout= (=C-x w L=).  Makes the named layout
  (created if new) the recent layout, captures the current frame into
  its =:saved-state=, clears its =:working-state=, and writes.  Unlike
  =workspace-save= it does not sync the file list (=:buffer-files=).
- =workspace-new=.  Stamps the freshly built =home= layout as its
  =:saved-state= and writes.

Autosaves (write =:working-state= only):

- Leaving a workspace's tab.  An advice on =tab-bar-select-tab= and
  =tab-bar-switch-to-tab= captures the outgoing workspace's window
  state into its recent layout's =:working-state=, then writes.  Every
  command that selects an existing tab goes through these (=C-x t o=,
  clicking a tab, =workspace-switch=, =workspace-restore= of a
  workspace that already has a tab).  Opening a /new/ tab does not
  (=C-x t 2=, =workspace-new=, =workspace-restore= of a workspace with
  no tab yet), so it captures nothing.  Skipped when the tab being left
  is not a workspace's, or when an anti-save predicate fires.
- Intra-workspace layout switch (=workspace-switch-layout=, =C-x w l=,
  and =workspace-switch-to-recent-layout=, =C-x w T=).  Captures the
  outgoing layout's window state into its =:working-state= and writes,
  before painting the destination layout.  This capture does /not/
  consult =workspace-anti-save-predicates=.
- =kill-emacs-hook=.  Captures the current workspace's =:working-state=
  (skipped if an anti-save predicate fires), then writes the registry
  regardless, so updates made earlier in the session still reach disk.
- Optional: =workspaces-mode='s idle timer (see *Idle save (opt-in)*),
  which consults the predicates and skips both capture and write when
  one fires.

Other commands that change the registry also write at once:
=workspace-revert=, =workspace-re-anchor=, =workspace-delete= and
=workspace-purge=.  =workspace-delete-layout= and
=workspace-remove-buffer= (which drops the file from =:buffer-files=)
do not; their changes reach disk with the next write.

No write happens while persistence is suppressed after an unreadable
state file (see below).

** Restore

Startup does /not/ recreate tabs.  When the package loads it reads the
state file and fills the registry — names, homes, layouts — and checks
each =:home= (see *Broken workspaces*), but it creates no tab and
changes no window.  The tab bar shows only the tabs Emacs started with.

A saved workspace becomes a tab when you restore it:

- =workspace-restore= (=C-x w o=) completes over every registered
  workspace, including those with no tab.  If the workspace already
  has a tab, it selects it.  Otherwise it opens a new tab named after
  the workspace and paints the workspace's recent layout, its buffers
  reincarnated as described under *Buffer reincarnation*.  A workspace
  with no saved layout gets =workspace-home-builder= instead (by
  default, =home.org= in a single window).
- Jumping to a portable bookmark from a tab that is not a workspace
  offers to restore one the same way (see *Off-workspace jumps*).

=workspace-switch= (=C-x w s=) only offers workspaces that already have
a tab; it never creates one.

The layout painted is the recent layout's =:working-state= when
non-nil, else its =:saved-state=.  The =workspace-revert= command
(=C-x w r=) is the "undo my drift" affordance: it clears
=:working-state= and re-applies =:saved-state= on demand.

When the persistence file is *missing*, the package starts silently
with no workspaces (no notice, no error); the first write creates the
file and its directory.

When the file is *present but unreadable* (a parse/=read= failure), the
package does NOT silently start empty and overwrite it.  It preserves
the file by renaming it to =workspaces.eld.corrupt-<timestamp>=, warns
(naming the backup path), and suppresses all persistence writes for the
session so an autosave cannot clobber the backed-up data with an empty
registry.  Serialization is readable by construction (buffer-bearing
window parameters such as =window-preserved-size= are translated to
readable forms and bookmark records are scrubbed of unreadable objects),
and every write is atomic (temp file + rename) and verified =read=-able
before it is committed — so the package does not itself produce an
unreadable file.

** State format is pre-alpha

The on-disk schema may break between refinement cycles.  There is no
migration code beyond reading the previous version: a v3 file is read
as v4 and upgraded in place by the next save.  A file of any other
version is ignored, not protected:
the first write of the session replaces it, at the latest the
=kill-emacs= write when Emacs exits.  If you see the
version-mismatch notice on startup and want to keep the old file, copy
it aside before saving; otherwise delete
=state/workspaces/<machine-role>/workspaces.eld= and recreate
your workspaces by hand on the current reader.  This policy is
intentional (design.md §D3): a real migration story is reserved for
beta.

The same holds in the other direction.  Code older than v4 (a checkout
of an older commit, a revert, a bisect) reads only v3: it ignores a v4
file with its version notice and then overwrites it with its empty
registry on its first save, at the latest when Emacs exits.  Until
=.tasks/workspaces-version-mismatch-state-file-overwritten.md= is
fixed, copy =workspaces.eld= aside before running older code against
the same state directory, and put it back afterwards.

* Buffer reincarnation

When restoring a workspace's window configuration, each window-state
leaf needs a /buffer/ — not just a name to look up.  The MVP looked
buffers up by name (=window-state-put='s default), which worked only
for file buffers that happened to be reopened first and ignored
point, narrowing, and major-mode state entirely.

The v2 package embeds a =workspace-buffer= struct in each leaf's
=parameters= map at capture time and uses it to reincarnate the leaf
at restore time.  Each struct carries:

- A bookmark record produced by =bookmark-make-record= — the
  standard Emacs bookmark API.
- The buffer's filename (or nil for non-file buffers).
- The buffer's name string.
- Flags for narrowed / indirect buffers.

** The fallback chain

On restore, each leaf walks a closed-set chain of strategies.  Step 1
has three possible answers — a buffer (done), a failure (go on to
step 2) or a decline (the gate below) — and steps 2 to 4 are tried in
order until one produces a live buffer:

1. =bookmark= — call =bookmark-handle-bookmark= on the saved record.
   Restores point position, narrowing region, and any
   major-mode-specific state.  Works for non-file buffers
   (=magit-status=, =eshell=, =*Messages*=) via their registered
   bookmark handlers.
2. =filename= — =find-file-noselect= on the saved filename.  Used
   when the bookmark restore errored or returned no buffer.
3. =name= — =get-buffer= on the saved name.  Last-ditch lookup for
   buffers that exist in-session but have no bookmark / filename.
4. =error-buffer= — a clearly named buffer describing what failed.
   The window slot is never left empty; a failed reincarnation is
   visible, not silent.

*The decline gate.*  A bookmark handler that signals
=workspace-restore-declined= (core's decline condition, a child of
=user-error=) has DECLINED to restore its buffer — a message for the
user, not a failure.  The portable-bookmarks module (see *Portable bookmarks*
below) does this whenever a leaf's bookmark cannot be resolved in the
workspace being restored: the file is not on this branch
(=not-on-branch=), more than one checkout could hold it
(=ambiguous=), the workspace holds no checkout of the repository
(=missing-repo= — a restore never asks the three-way question a
direct jump would), or no checkout of the repository in view can be
used — none at all, only another workspace's own clone, or discovery
failed (=no-clone=).  A declined leaf skips steps 2 and 3 and lands
directly on the error buffer, which shows the reason and says the
saved filename was deliberately NOT opened: that filename is the path
the buffer had when the layout was captured — very often another
workspace's copy of the file — which the handler has just refused.
Every declined leaf of one restore is reported in a single message,
never one prompt or one message per window.  Buffers whose bookmark
carries no repository stamp (files outside git, untracked files,
anything else the module does not stamp) are unaffected and restore
exactly as before.  Any
other error in step 1 — a stock handler's own =user-error= included,
such as Info reporting that its file does not exist — is a failure and
falls through to step 2 as before.

Restoring a leaf does not suppress questions: a handler that asks
while visiting — the large-file prompt, the unsafe local variables
query — asks as on any other visit.  While a leaf is restored,
=workspace--restoring-layout-leaf= is non-nil; a module whose handler
would ask a question of its own for every leaf (the portable-bookmarks
missing-repo choice) reads it and signals =workspace-restore-declined=
instead.

The four step names are closed-set-enforced at the code level via
=workspace--valid-reincarnation-steps= and the
=workspace--reincarnation-step-p= predicate.  Adding a fifth step
is a deliberate change (both the defconst and the chain logic move
together).

** Per-leaf failure isolation

Read-time errors on a single leaf — most notably the =help-mode=
bookmark =bug#56643=, where a natively-compiled subr fails to read
back — are trapped per leaf.  One unreadable bookmark causes that
leaf alone to fall through to the next step in the chain; the rest
of the layout restores normally.

** Restore ordering

The =window-state-put= call is deferred via =(run-at-time nil nil
...)= so the restore does not race against =bookmark--jump-via='s
own buffer-display call.  The user observes no delay; this is just
"don't fight the bookmark protocol."

* Portable bookmarks

** The problem

An Emacs bookmark stores an absolute =filename=.  In a
worktree-per-workspace workflow the same file exists in several
checkouts of one repository — the main clone plus one git worktree per
workspace — and a bookmark points into whichever checkout was current
when it was made.  Jumping to it from another workspace silently opens
/that/ workspace's copy, on another branch: an edit lands on the wrong
branch and nothing says so.  Once the owning workspace is purged the
bookmark points at nothing.

The portable-bookmarks module (=config/workspaces/portable-bookmarks.org=)
makes a bookmark mean "this file of this repository", and resolves it
against the workspace you are standing in when you jump.  It covers
every jump that goes through Emacs's bookmark machinery: =C-x r b=, the
other-window and other-frame variants, completion front-ends such as
=consult-bookmark=, and the layout restore described under *Buffer
reincarnation*.

** What is stored

When a bookmark is made for a file or directory that git tracks in a
repository with a remote, the record gains three extra properties: the
repository's identity (its remote URL normalized so that the SSH and
HTTPS spellings agree, e.g. =github.com/moogah/emacs=; =origin= is
preferred, a sole remote of another name is used, credentials in the
URL are dropped), the path relative to the repository root as git
spells it, and a format version.  Everything else about the record is
unchanged — in particular the absolute =filename= is kept.  A stock
Emacs therefore still reads and uses the bookmark file, and the stamp
costs nothing if the module is ever removed.

Records that cannot be stamped are left exactly as Emacs made them:
files outside any repository, untracked files, repositories with no
remote (no remote, no identity — a local path would mean nothing on
another machine), remote (TRAMP) files, and records that hold nested
records or window trees rather than one location (e.g. =tab-bookmark=).
Bookmarks made before the module existed are unstamped too.  All of
them keep working exactly as before.

** Which checkouts count

Resolution sorts every checkout it meets into one of three kinds:

- /workspace-owned/ — a checkout inside a registered workspace's home,
  the home itself (a workspace anchored at an existing repository with
  =C-u= =workspace-new=), or a clone that /contains/ the home (a
  workspace anchored at a subdirectory of a clone is working in that
  clone).  The one exception: a home that is a linked worktree kept
  inside its own main clone (=<clone>/.worktrees/x=) does not make
  that clone workspace-owned.  A workspace's own checkouts — the ones
  a bookmark resolves into — are its home, when the home is a
  checkout, and the checkouts directly under it
  (=~/emacs-workspaces/<name>/<repo>/=).
- /canonical/ — a repository's main worktree that no workspace owns.
  It is the only checkout that may ever be offered from outside the
  workspace, and only on an explicit choice.
- /other/ — anything else: in particular a linked worktree no workspace
  owns, which is never offered as "the" copy of a repository.

The checkouts /in view/ are the current workspace's, then every other
registered workspace's, then the repository this Emacs was loaded
from; git names each one's main worktree.  Nothing scans the disk
beyond that, so a clone that no workspace has a worktree of is not in
view.  Symbolic links in a workspace home are ignored: add a worktree
rather than linking a checkout in.

** The outcome table

Every jump to a stamped bookmark ends in exactly one of six outcomes:

| Outcome         | When                                                            | What you see                                       |
|-----------------+-----------------------------------------------------------------+----------------------------------------------------|
| =resolved=      | the workspace holds one checkout; the path is there             | its copy opens, through the bookmark's own handler |
| =not-on-branch= | the workspace holds one checkout; the path is not on its branch | a report; nothing opened                           |
| =ambiguous=     | two or more candidate checkouts                                 | a report naming them; nothing chosen               |
| =missing-repo=  | the workspace holds none; one canonical checkout in view        | a three-way choice (below)                         |
| =no-clone=      | no canonical checkout in view                                   | a report; nothing opened                           |
| =non-portable=  | no usable stamp                                                 | stock Emacs: the stored absolute path opens        |

A =resolved= jump keeps everything the bookmark normally restores:
position, Dired, Org, PDF.  =not-on-branch= also covers a directory
where a file was bookmarked, or the reverse.  =ambiguous= means the
workspace holds two or more checkouts of the repository (two sibling
worktrees in its home, say), or holds none while two or more separate
main clones are in view.  Each report is a single message naming the
bookmark and the repository.

Two rules hold across the table.  *The main checkout is never a silent
fallback*: it is opened only when you pick "view read-only" at the
=missing-repo= choice.  And *when two candidates are in view, nothing is
chosen for you*: picking the first would be choosing a branch by
directory order, so =ambiguous= reports and opens nothing.  Two
worktrees of /one/ repository elsewhere in view are not ambiguous — they
share one main worktree.  Only =non-portable= ever opens the stored
absolute path by design; a declined jump opens nothing and leaves no
bookmark mark in the buffer you were in.  Two failure paths are the exception: if the jump code itself errors on
a bookmark with no portable coordinates, it is opened as stock Emacs
would (its stored path) rather than not at all — for a portable
bookmark the jump declines and names the error — and during a layout
restore a leaf whose bookmark handler itself errors (as opposed to
declining) falls through the reincarnation chain to its saved filename.

The stored relative path is taken as spelled.  A bookmark reached
through a symbolic link that the repository tracks resolves to the same
spelling inside your checkout, wherever that link points on your
branch — exactly what visiting the path by hand would open.  A
hand-edited stamp whose path is absolute or climbs out with =..= is
treated as unstamped, and the jump behaves as stock.

** The missing-repo choice

=missing-repo= is the one outcome where a useful action exists but has
to be chosen.  The prompt names the bookmark, the workspace, the
repository and the canonical checkout, and offers:

- /add a worktree here/ — creates a worktree of the canonical checkout
  the resolver found, inside the current workspace's home, through the
  git-worktree integration.  You are not asked for a source repository
  again; you are asked only for the branch name (defaulting to the
  workspace name).  The new worktree is branched off the repository's
  main branch, and the bookmark is resolved once more against it: the
  file opens if it exists there, and otherwise the jump reports why
  (typically =not-on-branch=, for a file that only exists on the branch
  where it was bookmarked) without asking again.
- /view read-only/ — opens the canonical checkout's copy in =view-mode=
  and adds a =[canonical …]= marker to the mode line naming the
  checkout.  The marker stays for the life of the buffer: it survives
  =C-x C-q= (the deliberate way to make the buffer writable) and a
  =revert-buffer=, so the buffer always says what it is.
- /cancel/ — opens nothing.

An option that cannot work is withheld, and the prompt says why:
"add a worktree" needs a usable current workspace (registered, not
broken, with a home that is an existing local directory) and the
git-worktree module loaded; "view read-only" is
withheld when the canonical checkout does not have the file.  During a
layout restore nothing prompts: the leaf declines with the
=missing-repo= report instead (see *Buffer reincarnation*).

For the ordinary =C-x w= /Integrations/ "git worktree" command, which
does ask for a source repository, the candidates come first from the
checkouts in view (each resolved to its canonical checkout) and then
from magit's repository list, which this configuration points at the
repositories directly under =~/src= when that directory exists.  Only
canonical checkouts are offered from either source.

** Off-workspace jumps

A stamped bookmark needs a workspace to resolve against.  Jumping to one
from a tab that is not a workspace does not open the stored path;
instead it asks which workspace should serve the jump.  The candidates
come from the /registry/, not from live tabs, so this works right after
a restart when the workspace has no tab yet.  Workspaces that already
hold a checkout of the repository are listed first and annotated as
such, and the first of them is the default; broken workspaces are not
offered.

The chosen workspace is restored exactly as =workspace-restore= would
(its tab created and its layout painted, or, when the tab already
exists, simply selected), and the bookmark is
then resolved against it through the table above.  A =resolved= file
opens in the selected window of the restored layout — same window, no
split.  The result is remembered like any other file you open in that
workspace: the next autosave records it in the workspace's
=:working-state=, and =:saved-state= is untouched as with every
autosave.

=C-g= at the workspace prompt ends the jump: nothing restored, nothing
opened.  When a workspace holds the repository, the first holder is the
default and an empty answer (plain =RET=) restores it: "no workspace"
is not offered then.  When no workspace holds it, an empty answer —
=M-RET= (=vertico-exit-input=) under vertico, whose plain =RET= picks the
highlighted candidate — or no workspace to offer at all, means "no
workspace": the bookmark is resolved against none, and the only thing that can
follow is the =missing-repo= choice without "add a worktree" (view
read-only, or cancel), or a report.  In a non-interactive Emacs, or
wherever no question may be asked, the jump declines with a message
instead of prompting.  Unstamped bookmarks are not affected: off a
workspace they open their stored path as always.

** Two bookmark systems

This section is about the user-facing bookmark list (=C-x r m=,
=C-x r b=, stored in =bookmark-default-file=).  The layouts in
=workspaces.eld= carry bookmark records of their own, one per window
(see *Buffer reincarnation*).  The two are separate stores, but both go
through the same Emacs functions, so layout records are stamped the same
way and a restored layout's windows are resolved against the workspace
being restored, with the decline gate described there.

** Scope and limitations

- One location per record.  Records holding nested records or window
  trees (e.g. =tab-bookmark=) are left alone, and no property other than
  the record's own =filename= is resolved.
- Stamps are trusted: after =bookmark-relocate= (or a hand edit) a
  record keeps its old stamp and resolves to the pre-relocation file
  from other checkouts — a known limitation.
- Not part of this module, each separate future work: sharing
  bookmarks between machines (and deciding where a shared bookmark
  file lives — see =state/bookmarks/README.md=), bookmarks that restore
  a workspace at a named layout, portable layouts, and workspace
  templates.

** Removing the module

The module is droppable.  It is loaded by one =jf/load-module= line in
=config/workspaces/workspaces.org=; removing that line removes both
advices at the next start (=M-x workspace-bookmark-remove-advice= does
the same in a running session), and every bookmark goes back to its
stored absolute path, layout windows included.  Nothing is lost: the
stamps stay in the files as inert extra properties that stock Emacs
ignores, and they are used again if the module comes back.  The
workspaces core does not depend on it.  The one visible difference
elsewhere is the git-worktree command's repository picker, which loses
its checkouts-in-view source and offers magit's repository list
without checking which entries are canonical.

* Working-state revert

=workspace-revert= (=C-x w r=) is the "undo my drift" command.
When you have been rearranging windows since the last explicit
=workspace-save= and want to abandon the rearrangement, =C-x w r=:

1. Clears the =:working-state= of the current workspace's recent
   layout.
2. Writes the registry to disk.
3. Re-applies that layout's =:saved-state= via the standard restore
   path (buffer reincarnation included).

If =:working-state= is already nil, =workspace-revert= still
re-applies =:saved-state= — a useful "reset to my last clean save"
gesture even when nothing has accumulated to discard.

The command errors off-workspace; it requires a tab registered with
the workspaces package.

* Idle save (opt-in)

=workspaces-mode= is a global minor mode that adds a third
persistence path: a periodic idle-timer capture of the current
workspace's =:working-state=.  It is a crash-safety net atop the
explicit saves and the tab-switch, layout-switch and =kill-emacs=
autosaves; those run whether or not the mode is on and are unaffected
by it.

The mode is /off by default/.  Enable it explicitly:

#+begin_src emacs-lisp
;; in init.org (or anywhere user-level config runs after the
;; workspaces package has loaded)
(workspaces-mode 1)
#+end_src

…or interactively via =M-x workspaces-mode=.

** What it captures

When the timer fires, the callback short-circuits if the user is not
on a workspaces-managed tab.  Otherwise it writes the current
window-state into the recent layout-group's =:working-state= slot —
the same slot the tab-switch autosave uses — and writes the registry
to disk at once.  The idle save /never/ touches =:saved-state=; the
explicit saves (=C-x w S=, =C-x w L=, and the home stamp written by
=workspace-new=) remain the only way to update the explicit baseline.

** Customization

=workspaces-mode-idle-frequency= — seconds of idle time before the
timer fires.  Default: =60=.  The timer fires once each time Emacs
has been idle that long (an Emacs idle timer does not repeat within
one idle period), so a long idle stretch produces one save, not one
per minute.  The value is read when the mode is turned on; toggle the
mode after changing it.

The default is deliberately conservative: tab-switch autosave already
covers most intra-session state, so idle save is purely the crash-
safety net.  Sixty seconds of work is a tolerable loss window;
shorter intervals trade disk churn for marginal recovery.

Set to =nil= to disable the idle trigger while keeping the mode
"on" (rare; the explicit save and tab-switch autosave remain active
either way).

** Interaction with anti-save predicates

The idle tick consults =workspace-anti-save-predicates= before it
calls =workspace--autosave-current-layout= (the predicates are checked
by the callers, not inside that function: the tab-switch advice, the
idle tick and the =kill-emacs= flush check them; the layout-switch
capture in =workspace-switch-layout= does not).  No capture and no
write happen during debugger activity, minibuffer interaction, or other
states a user has declared off-limits.

* Buffer membership

Buffer membership is per-workspace.  When a buffer is displayed in
any window of a workspace, it becomes a member of that workspace via
=bufferlo='s per-tab buffer-list scope.  Completion-based buffer
commands (=switch-to-buffer=, =consult-buffer=, …) are filtered to
the current workspace's membership.

A buffer may be a member of multiple workspaces simultaneously.

** =kill-buffer= vs =workspace-remove-buffer= (Story A)

=kill-buffer= (=C-x k=) is /not/ shadowed, advised, or rebound.  It
ends the buffer's life globally, removing it from every workspace's
membership as a side effect.  This preserves universal Emacs
convention: =C-x k= always means "end this buffer."

=workspace-remove-buffer= (=C-x w b=) is the additive "I'm done with
this here" command.  It removes the buffer from the /current/
workspace's membership without killing it.  Other workspaces that
hold the same buffer remain unaffected.

* Deferred features

These are designed-for but not implemented in v2.

- Multiple timestamped layout revisions per layout-group (a single
  =layout-group= can hold a list of layouts; today it always holds
  exactly one).  Commands to browse and restore prior revisions are
  not implemented.
- Per-layout-group git observations.  The layout's =:etc= alist would
  host them; today it holds only the layout metadata (=origin=,
  =description=, =source=, see *Programmatic layouts*), and nothing
  records git observations.
- Restoring an explicit "selected tab at save time" — the state file
  does not record which workspace was selected, and startup restores
  no tabs, so Emacs starts on its own initial tab rather than the
  previously-selected workspace.
- A =workspace-rename= command.  Today, renaming a workspace is an
  out-of-band action: =mv= the home directory, then on next load
  the workspace surfaces as broken (its persisted =:home= no longer
  exists; see *Broken workspaces* above).  Run =workspace-re-anchor=
  (=C-x w R=) and point it at the new directory; the registry entry
  is renamed in place to match the new basename.

* Implementation notes

- Built on =tab-bar-mode= directly; does not use
  =activities-tabs-mode=.
- Buffer scoping via =bufferlo= (per-tab buffer list).
- Window configurations captured via =window-state-get= / restored
  via =window-state-put=, with the per-leaf =workspace-buffer=
  parameter (see *Buffer reincarnation*) carrying the bookmark
  record and identifying metadata.
