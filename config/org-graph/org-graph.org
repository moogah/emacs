#+auto_tangle: y

A layered knowledge-graph spike over [[https://github.com/d12frosted/vulpea][vulpea]] (v2.4+), plugged into the
=workspaces= substrate. org-graph indexes the durable concept vault
(=~/org/roam/=) plus each active workspace =:home=, extracts typed
semantic edges from a PROPERTIES-drawer convention, exposes
schema-backed note-type finders, and registers an agent-facing
query/write surface into gptel and the =workspace-assistant= preset.

This file is the top-level loader for the =org-graph= module. Behavior
is implemented incrementally in submodules under =config/org-graph/=;
they are loaded from the [[#submodules][Submodules]] section as they land.

org-roam runs unchanged alongside this module for the duration of the
spike — see =openspec/specs/org-graph/spec.md= (Coexistence with
org-roam) and =openspec/changes/org-graph-spike/design.md=.

* Packages
:PROPERTIES:
:CUSTOM_ID: packages
:END:

vulpea is the single index/discovery engine for the spike (RE-2:
org-node is *not* adopted — vulpea already keeps =org-id-locations=
populated via =org-id-add-location=, so a second index would be
redundant double-work).

The recipe is pinned to a specific commit rather than =master=. Pinning
is ordinary hygiene here, not a spike-survival mechanism: vulpea 2.4's
parser-epoch cache invalidation, schema-version auto-rebuild, and
async-default sync retired the original "API still evolving" risk
(RE-6).

Pin = release tag =v2.4.0= (commit
=0f55c96b6649872155d5486acb749710b3726e4a=). straight.el does *not*
honour a recipe-level =:commit= keyword — version pinning is otherwise
done through a profile *versions lockfile*, which this config does not
maintain. straight *does* pass =:branch= to =git clone --branch=, and
git accepts a tag name there, so =:branch "v2.4.0"= checks out the
release tag (detached HEAD at the commit above). That is the
working, declarative pin and it satisfies the task's "v2.4.x release
tag/commit" requirement. A profile lockfile entry is the production-grade
follow-up if the spike survives.

Change detection prefers =fswatch= on macOS; if it is not installed,
vulpea falls back to fd/find polling, so the spike does not require it.

=:config= pins =vulpea-db-location= to the isolated runtime path (D8 /
=register/invariant/vulpea-db-isolation=) and otherwise stays minimal —
directory sync and autosync wiring belong to the =registry-discovery=
task, not here.

D8 requires the org-graph index DB to live under the worktree runtime
=state/= dir (=runtime/state/vulpea/notes.db=), distinct from org-roam
and from vulpea's default (=runtime/vulpea.db=). Isolation is the
spike's clean-rollback property: wiping/rebuilding the org-graph DB then
never touches org-roam's DB or the =org-id-locations= cache.

The path is set here in the *loader's* vulpea =:config=, not in
=discovery/configure-sync=, because it MUST be fixed before any submodule
opens the DB: =discovery.el='s load-time =org-id-locations= seed calls
=vulpea-db-query= at module load, which would open the DB at the default
path before =configure-sync= ever runs. The loader's vulpea =:config=
runs eagerly when this block evaluates — before submodules load — so the
path is fixed first. =user-emacs-directory= resolves to this worktree's
=runtime/= dir (see =early-init.el=), so the path is worktree-isolated.
The directory is created if vulpea has not already done so.

#+begin_src emacs-lisp
(use-package vulpea
  :straight (vulpea :type git :host github :repo "d12frosted/vulpea"
                    :branch "v2.4.0")
  :config
  (setq vulpea-db-location
        (expand-file-name "state/vulpea/notes.db" user-emacs-directory))
  (make-directory (file-name-directory vulpea-db-location) t))
#+end_src
